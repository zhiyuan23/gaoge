# 前端样式规范

本规范用于约束各前端应用的样式方案边界，避免在 monorepo 内无序混用 CSS 工具。

## 原则

- 样式方案按应用边界管理，不追求全仓统一一种工具
- 优先沿用应用当前已存在、已跑通的样式栈，不为了“统一”而跨应用迁移
- 工具类方案只解决局部布局、间距、状态样式等高频问题，不替代清晰的组件结构和业务语义

## AI 开发默认写法

- 对已接入 `UnoCSS` 或 `Tailwind CSS` 的前端应用，AI 新增或修改界面样式时，默认优先使用模板内联的工具类写法
- 优先把布局、间距、字号、颜色、圆角、边框、阴影、显隐、交互状态等高频样式直接写在 `class` 中
- 只有在更适合抽离时，才使用传统 `className` / `class` + 独立 `css`、`scss`、`less` 写法
- 不为几条简单样式额外新建样式块，也不为了“看起来更整洁”把原本更直观的工具类强行回退成传统类名

更适合使用传统写法的典型场景：

- 同一组样式会在多个位置稳定复用，且已形成明确业务语义
- 需要表达较长、较复杂的选择器关系，例如后代选择器、兄弟选择器、深层覆盖、第三方组件覆盖
- 需要使用伪元素、复杂动画、关键帧、媒体查询，或工具类表达明显变差
- 需要承载主题变量、品牌皮肤、富文本内容区、编辑器内容区等块级样式
- 继续沿用当前文件内已经成型的样式组织方式，比强行改成工具类风险更低

不建议的写法：

- 把纯展示性的短样式统一塞进无语义的自定义类名
- 在支持工具类的应用里，同时对同一元素混用一套可被工具类直接表达的传统样式定义
- 为单个页面临时造一层样式抽象，却没有复用价值或可读性收益

## 当前应用边界

### `apps/admin`

- 当前使用 `Element Plus + UnoCSS + 项目既有样式约定`
- 页面布局、间距、容器、按钮区、状态色等高频样式，AI 默认优先使用 `UnoCSS` 工具类内联写法
- `SCSS` 主要保留给 `Element Plus` 深度覆盖、第三方组件样式调整、复杂选择器和已有全局样式资源
- 可以使用 `tailwind-merge` 处理类名合并，但这不代表 admin 页面默认采用 `Tailwind CSS`

### `apps/web`

- 当前使用 `Tailwind CSS`
- 新增页面与组件默认优先使用 `Tailwind CSS` 工具类内联写法
- 独立样式文件优先留给复用语义块、复杂动画、主题皮肤和不适合直接堆叠在模板中的样式

### `apps/miniapp`

- 允许并优先使用当前已接入的 `UnoCSS`
- `UnoCSS` 主要用于小程序页面中的原子化布局、间距、颜色和快捷样式表达
- AI 默认优先在模板中直接书写工具类；需要稳定复用或业务语义明显的样式，再回到组件封装和已有样式文件
- 不把所有视觉逻辑都压成工具类，尤其不要牺牲小程序模板可读性

### `apps/desktop`

- 允许并优先使用当前已接入的 `Tailwind CSS`
- 桌面端新增界面默认沿用 `React + Tailwind CSS` 现有模式
- AI 默认优先在 JSX 中直接组合 `Tailwind CSS` 类名
- 如需引入新的样式抽象，应先证明现有 `Tailwind CSS` 无法支撑，而不是先做风格迁移

## 限制

- 不因个人偏好在未使用该工具的应用中扩散 `UnoCSS` 或 `Tailwind CSS`
- 不把某个应用的工具类写法直接复制为另一个应用的默认规范
- 不把工具类样式当成跨应用共享层；跨应用共享应优先沉淀为 `packages/ui/*` 的令牌、契约或稳定组件能力

## 新增或调整规则时

- 若某个应用正式采纳、废弃或限制某种样式方案，应先更新本文档
- 若变化已经上升到仓库级协作要求，再同步更新 `AGENTS.md`
