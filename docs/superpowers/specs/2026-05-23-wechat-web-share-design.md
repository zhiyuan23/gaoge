# apps/web 微信内分享设计

日期：2026-05-23

## 目标

为 `apps/web` 增加微信公众号 H5 分享能力，使用户在微信内打开页面后，使用右上角分享时能稳定显示页面对应的：

- 标题
- 简介
- 缩略图

本次目标是：

- 在 `apps/api` 提供公众号网页 JS-SDK 签名接口
- 在 `apps/web` 接入微信 JS-SDK
- 按页面区分分享文案与缩略图
- 分享链接保持为当前页本身
- 在现有页面结构下以最小改动接入

本次先完成设计，不在此文档中展开实现代码。

## 背景

当前仓库中的前台站点 `apps/web` 已经具备真实业务页面，主要路由包括：

- `/`
- `/teams/:team?`
- `/teams/football/assets`

现状特点：

- `apps/web` 是 Vite + Vue 3 单页应用
- 前台请求层当前采用轻量 `utils/api.js` 封装
- `apps/api` 是 NestJS 应用，已经通过 `ConfigModule` 管理环境变量
- `apps/api/src/common/wechat/wechat.service.ts` 当前承担的是微信小程序登录能力，不是公众号网页分享能力

因此，这次不适合把公众号网页分享逻辑直接塞进现有小程序 `WechatService`。更稳妥的做法是新增一套面向公众号 H5 分享的独立能力，避免配置和职责混用。

## 范围

包含：

- `apps/api` 新增公众号网页分享签名能力
- `apps/api` 新增公众号专用环境变量
- `apps/web` 新增微信环境识别与分享初始化逻辑
- `apps/web` 为首页、球队页、资产页维护页面级静态分享配置
- 路由切换后重新设置当前页分享内容
- 为新增逻辑补充必要测试

不包含：

- 后台可配置分享中心
- 非微信浏览器下的特殊分享适配
- 按赛季、球队详情、运营活动等动态生成分享文案
- 为篮球页面单独扩展更多业务分享字段
- 修改数据库结构
- 修改现有小程序登录流程

## 方案对比

### 方案一：前端维护静态页面分享配置，后端只提供签名接口

做法：

- 前端按路由维护分享 `title / desc / imgUrl`
- 后端只返回 `appId / timestamp / nonceStr / signature`

优点：

- 与当前需求完全一致
- 变更最小，边界清晰
- 不引入额外后台配置模型
- 后端职责单一，便于测试和排错

缺点：

- 分享文案修改需要发版
- 后续如果营销活动频繁变化，需要再次扩展

### 方案二：后端统一返回签名和分享文案

做法：

- 前端按页面请求后端，由后端下发签名和分享内容

优点：

- 文案调整可只改服务端

缺点：

- 当前并没有后台配置需求
- 会把页面文案配置职责过早转移到后端
- 需要设计页面标识、文案来源和缓存策略，超出本次必要范围

### 方案三：增加后台分享配置中心

做法：

- 在后台维护页面分享素材，前后端都围绕配置中心实现

优点：

- 灵活度最高

缺点：

- 明显超出当前需求
- 需要新增管理页面、接口、权限和数据模型

## 结论

采用方案一：前端维护页面级静态分享配置，后端只提供公众号网页 JS-SDK 签名接口。

具体原则：

- 页面分享内容按当前路由区分
- 分享链接保持当前页面 URL
- 前端不直接持有公众号密钥
- 公众号网页分享能力与现有微信小程序能力分离实现
- 非微信环境不初始化 JS-SDK，避免引入无效报错

## 信息架构

### 页面与分享映射

本次按页面类型维护三套分享配置：

- 首页 `/`
- 球队页 `/teams/:team?`
- 足球资产页 `/teams/football/assets`

说明：

- 当前已确认“按页面区分”，未要求按球队、赛季、记录明细等更细粒度动态变化
- `teams` 页中的 `football` 与 `basketball` 暂时共用一套球队页分享配置
- 后续若要区分足球和篮球文案，只扩展前端配置选择逻辑即可，不影响签名接口设计

### 分享行为

微信内用户分享页面时：

- 分享给朋友使用页面对应的 `title / desc / link / imgUrl`
- 分享到朋友圈使用页面对应的 `title / link / imgUrl`
- `link` 始终为当前页面 URL 本身，不做统一跳首页或跳球队页处理

## 后端设计

### 模块边界

不复用现有 `apps/api/src/common/wechat/wechat.service.ts`。

原因：

- 现有 service 绑定的是小程序 `WECHAT_APPID / WECHAT_APPSECRET`
- 现有能力集中在 `jscode2session` 与手机号解密
- 公众号网页分享需要的是 `access_token / jsapi_ticket / signature`
- 两类场景的配置、接口和错误语义不同，混在同一个 service 中会增加维护成本

建议新增公众号网页分享专用模块，例如：

- `apps/api/src/modules/wechat-official-account/*`

模块职责：

- 读取公众号配置
- 获取和缓存 `access_token`
- 获取和缓存 `jsapi_ticket`
- 基于页面 URL 生成 JS-SDK 签名
- 暴露给 `apps/web` 使用的签名接口

### 环境变量

`apps/api` 新增公众号专用环境变量：

- `WECHAT_OFFICIAL_ACCOUNT_APPID`
- `WECHAT_OFFICIAL_ACCOUNT_APPSECRET`

说明：

- 不复用现有 `WECHAT_APPID`
- `.env.example` 需要同步补充说明
- 生产环境由服务端部署环境提供真实值

### 签名接口

建议新增接口：

- `GET /wechat/official-account/jssdk-signature?url=ENCODED_URL`

返回结构建议：

- `appId`
- `timestamp`
- `nonceStr`
- `signature`

说明：

- 返回结构尽量保持扁平，不叠加不必要元数据
- `appId` 返回公众号 `AppID`，供前端直接喂给 `wx.config`

### URL 处理规则

前端传入当前页面 URL，后端按微信签名要求处理。

规则：

- 使用完整 URL
- 去掉 hash 及其后续部分
- 保留协议、域名、路径和查询参数
- 不对查询参数重新排序

如果 `url` 缺失或格式非法，接口返回 400。

### access_token 与 jsapi_ticket 缓存

服务端需要做内存级缓存：

- `access_token`
- `access_token` 过期时间
- `jsapi_ticket`
- `jsapi_ticket` 过期时间

缓存原则：

- 在当前 Nest 进程内缓存即可
- 接近过期时重新拉取
- 不额外引入 Redis 或数据库缓存

原因：

- 当前需求量级下，单进程内缓存已足够
- 目标是尽快稳定落地，不提前引入跨进程缓存复杂度

### 错误处理

后端应区分以下错误：

- 请求参数错误：缺少 `url` 或 URL 非法
- 配置错误：未配置公众号 `AppID/AppSecret`
- 微信上游错误：获取 `access_token` 或 `jsapi_ticket` 失败

返回原则：

- 前端可感知为“分享初始化失败”
- 服务端日志中保留上游错误上下文，便于排查
- 不向前端暴露 `AppSecret`

## 前端设计

### 分享配置来源

前端在 `apps/web` 内维护一个静态配置表，按页面类型返回：

- `title`
- `desc`
- `imgUrl`

说明：

- 当前已明确由前端写死，不通过后端动态下发
- 以后如果确实要转为服务端下发，也只替换配置来源，不影响签名流程

### 微信环境识别

只在微信内置浏览器中初始化分享逻辑。

识别原则：

- 基于 `navigator.userAgent` 判断是否为 `MicroMessenger`
- 非微信环境直接跳过

原因：

- 避免普通浏览器控制台报 JS-SDK 相关错误
- 减少不必要的外部脚本加载和接口请求

### JS-SDK 初始化流程

页面进入或路由切换后执行：

1. 获取当前页面 URL，并去掉 hash
2. 请求后端签名接口
3. 调用 `wx.config`
4. 在 `wx.ready` 中设置：
   - `wx.updateAppMessageShareData`
   - `wx.updateTimelineShareData`

说明：

- `jsApiList` 只声明当前需要的分享接口
- 不额外接入未使用的定位、支付、上传等能力

### 路由切换处理

由于 `apps/web` 是 SPA，页面切换不会整页刷新，因此需要在路由变化后重新设置分享数据。

原则：

- 在全局层监听当前路由变化
- 路由变化时重新拉取签名并重设分享内容
- 以“当前页面已经渲染完成后触发”为准，避免拿到过早的 URL 状态

### 分享图片要求

分享缩略图使用固定 HTTPS 绝对地址。

要求：

- 图片可公网访问
- 使用正式 HTTPS 地址
- 不依赖登录态
- 不使用本地开发地址

本次不在设计中强制规定图片尺寸，但实现时应优先使用稳定的方图素材。

建议新增：

- `src/modules/wechat-official-account/wechat-official-account.module.ts`
- `src/modules/wechat-official-account/wechat-official-account.service.ts`
- `src/modules/wechat-official-account/wechat-official-account.controller.ts`

并在 `AppModule` 中注册该模块。

### `apps/web`

建议新增：

- 分享配置文件
- 微信分享初始化逻辑
- 与路由联动的全局调用入口

组织原则：

- 分享配置与微信 SDK 调用逻辑分开
- 页面配置纯数据化
- SDK 调用逻辑独立封装，避免散落在各页面组件中

## 测试设计

### `apps/api`

补充单测覆盖：

- 未配置公众号环境变量时报错
- 缺少 `url` 参数时返回错误
- URL 去 hash 的签名输入正确
- 缓存命中时不重复请求微信上游
- 微信上游返回错误时正确抛出异常

### `apps/web`

补充测试覆盖：

- 路由到首页时选中首页分享配置
- 路由到球队页时选中球队页分享配置
- 路由到资产页时选中资产页分享配置
- 非微信环境下不执行初始化
- 微信环境下会请求签名并设置分享数据

### 联调验证

真机微信联调时验证：

- 首页分享卡片标题、简介、缩略图正确
- 球队页分享卡片标题、简介、缩略图正确
- 资产页分享卡片标题、简介、缩略图正确
- 分享出去的链接就是当前页
- 路由切换后再次分享，卡片内容会随页面变化

## 配置与部署要求

公众号后台需要完成：

- 配置 `JS接口安全域名`
- 按公众号后台要求放置域名校验文件
- 使用正式 HTTPS 域名访问页面

说明：

- 本地 `localhost` 不作为真机微信联调目标
- 若前后端域名不同，只要分享页面所在域名已配置为 `JS接口安全域名` 即可

## 风险与后续扩展

### 已知风险

- 微信对分享卡片存在缓存，联调时可能出现修改后未立即生效
- 如果分享图片地址不可访问或证书异常，缩略图可能不展示
- 若后续需要将球队页拆分为足球和篮球不同文案，需要扩展前端配置选择逻辑

### 后续可扩展方向

- 将 `teams/football` 与 `teams/basketball` 拆分为不同分享配置
- 将静态文案迁移为服务端配置
- 增加运营活动页、详情页的细粒度分享模板

## 实施结论

本次采用“前端页面级静态分享配置 + 后端公众号 JSSDK 签名接口”的最小可行方案。

这样可以：

- 直接满足微信内分享缩略图和简介展示需求
- 保持实现边界简单
- 不污染现有小程序微信能力
- 为后续按页面、按业务逐步扩展保留空间
