# Banner 拖拽排序设计

## 背景

`apps/admin` 的 Banner 管理页当前通过 `sort` 数值字段人工录入排序，交互成本高，也容易在多条 Banner 调整时出错。

当前列表本身是无分页全量列表，后端按 `sort desc, id desc` 返回数据，适合改为后台表格拖拽排序。

## 目标

- 将 Banner 管理页的排序主交互从手动输入改为表格拖拽
- 拖拽完成后立即保存，无需额外“保存排序”按钮
- 仅允许在未筛选的完整列表下拖拽，避免在局部结果里误改全局顺序

## 非目标

- 不将 `EsTable` 抽象成通用拖拽表格组件
- 不为本次需求新增通用批量排序基础设施
- 不支持在筛选结果中拖拽排序

## 方案

### 后端

在现有 Banner 模块上新增排序接口：

- `PATCH /content/banners/reorder`

请求体传入完整顺序数组，例如：

```json
{
  "items": [
    { "id": 12, "sort": 300 },
    { "id": 9, "sort": 200 },
    { "id": 3, "sort": 100 }
  ]
}
```

约束：

- 必须至少包含一条记录
- 所有 `id` 必须存在
- 通过事务逐条更新 `sort`
- 返回最新排序后的 Banner 列表，保持与列表接口一致的排序规则

之所以使用批量接口，而不是前端逐条调用现有 `PATCH /content/banners/:id`：

- 拖拽是一个“整体重排”动作，应作为一次原子更新处理
- 能避免前端一次拖拽触发多次请求和中间态闪动
- 代码改动仍然局限在 banner 模块内，没有扩散成通用能力

### 前端

在 `apps/admin/src/views/sports/content/banner/index.vue` 内部接入行拖拽：

- 使用 `SortableJS` 直接绑定当前页面表格 `tbody`
- 仅当搜索条件等于默认值时启用拖拽
- 有任一筛选条件生效时：
  - 不初始化拖拽
  - 页面显示“请清空筛选后再拖拽排序”之类的提示

拖拽成功后：

1. 基于当前表格顺序生成新的排序数组
2. 立即调用批量排序接口
3. 成功后提示“排序已更新”
4. 重新请求列表，保证界面与服务端一致

失败时：

- 提示错误
- 重新拉取列表，回滚本地顺序

### 排序值策略

前端按当前拖拽后的显示顺序重新生成离散排序值，例如从前到后使用：

- `list.length * 100`
- `(list.length - 1) * 100`
- ...
- `100`

这样能保持现有“数值越大越靠前”的语义，也给后续手工微调保留间隔。

## 权限

复用现有 `content.banner.update` 权限，不新增单独的排序权限点。

## 测试

后端增加单测覆盖：

- 批量排序接口对应 service 在事务中更新全部记录
- 缺少记录时抛出异常
- 返回结果仍按 `sort desc, id desc` 排序

前端至少做功能性校验：

- 默认完整列表可拖拽
- 有筛选条件时拖拽禁用
- 拖拽后立即调用排序接口并刷新列表
