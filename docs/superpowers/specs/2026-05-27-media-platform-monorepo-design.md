# 独立媒体平台 Monorepo 设计

## 背景

当前 `gaoge` 仓库中的 `apps/web` 已承担官网职责，不再适合作为新内容产品的承载容器。

现在要规划的是一条独立产品线：一个完整的媒体平台，而不是官网下的资讯栏目。该产品线需要同时覆盖读者站点、编辑后台和内容服务，因此需要单独评估仓库边界、应用划分和技术栈。

本次设计解决以下问题：

- 是否继续留在当前仓库
- 新产品线的 monorepo 结构如何划分
- 新产品线的工程命名如何落地
- `site / cms / api` 的技术栈如何选择

本次设计不进入实现计划、数据库模型、页面原型或部署细节。

## 已确认前提

- 这是一个独立产品线，不再视为高歌官网的附属内容站
- 产品形态是完整媒体平台，而不是单一新闻站点
- 新平台采用独立 monorepo，更适合独立发布、独立团队协作和独立治理
- 平台需要 `site + cms + api` 全独立成套
- 读者端 UI 体验和整体视觉质量优先，因此前端生态优先选择 React
- UI 体系倾向 `shadcn/ui` 或同类 React 生态方案

## 仓库边界结论

### 不推荐继续留在当前 `gaoge` monorepo

继续放在当前仓库的短期好处只是启动更快，但长期会出现以下问题：

- 发布节奏和当前产品线互相牵制
- 前端和后台技术选型被旧应用边界限制
- 内容模型、权限、发布流、SEO、媒体资源管理逐渐形成独立领域后，会与现有业务边界混杂
- CI/CD、环境变量、域名、监控和权限治理难以彻底解耦

### 推荐新建独立 monorepo

新仓库更符合“独立产品线”的实际治理方式：

- 独立版本和发布节奏
- 独立环境、域名和部署流水线
- 独立工程规范和依赖升级节奏
- 独立内容领域模型与后台能力演进

## 工程命名

虽然新仓库会独立存在，但命名仍然遵循“目录名表达产品角色，不表达技术名”的原则。

### 仓库内应用命名

- `apps/site`
- `apps/cms`
- `apps/api`

### 共享层命名

- `packages/shared`
- `packages/sdk`
- `packages/ui`

这样命名的原因：

- `site` 明确表达读者端站点职责，避免使用过于模糊的 `web`
- `cms` 明确表达编辑后台职责，避免把内容管理继续混进通用 admin
- `api` 作为统一内容服务层，能同时服务站点和 CMS

## 产品结构

### `apps/site`

职责：

- 对外内容站
- 首页、栏目页、文章页、专题页、作者页、搜索页
- SEO、Open Graph、分享卡片、内容分发和读者体验

原则：

- 以读者访问性能和内容消费体验为中心
- 能承载静态生成、增量更新和服务端渲染能力
- 不承担编辑端逻辑

### `apps/cms`

职责：

- 编辑和运营后台
- 稿件、栏目、标签、作者、专题、媒体资源、发布流程管理
- 草稿、预览、审核、发布、下线、审计等后台能力

原则：

- 以内容生产效率和后台操作体验为中心
- 与对外站点视觉体系共享基础设计语言，但不共享页面级业务结构

### `apps/api`

职责：

- 为 `site` 和 `cms` 提供统一内容服务
- 提供鉴权、内容建模、发布状态管理、媒体资源管理、审计日志、检索接口

原则：

- 不直接耦合站点渲染实现
- 站点和 CMS 通过稳定契约访问内容能力

### `packages/shared`

职责：

- 运行时无关的领域类型、schema、枚举、常量

原则：

- 不依赖应用层
- 只沉淀真正稳定的内容领域契约

### `packages/sdk`

职责：

- 给 `site` 和 `cms` 使用的 API 客户端和请求封装

### `packages/ui`

职责：

- 稳定的 React UI 基础层
- 设计令牌、基础组件、布局原语和常用交互外壳

原则：

- 共享的是基础能力，不是站点页面本身
- 不把内容站和 CMS 的具体业务页面耦合进共享包

## 技术栈结论

### 推荐组合

- `apps/site`：`Next.js`
- `apps/cms`：`Next.js`
- `apps/api`：`NestJS`
- UI 基础：`shadcn/ui`
- 样式体系：`Tailwind CSS v4`
- 类型与校验：`TypeScript + zod`

### 为什么 `site` 选择 `Next.js`

媒体平台的读者站点不是普通后台壳应用，核心诉求包括：

- SEO 和搜索引擎收录
- 文章详情页首屏性能
- 静态生成和增量更新
- 元信息、Open Graph、分享卡片
- 更自然的服务端获取和页面级渲染策略

这类能力从一开始就比 `Vite SPA` 更匹配 `Next.js`。

### 为什么 `cms` 也选择 `Next.js`

虽然 CMS 不以 SEO 为主，但保持同一 React 框架可以带来明显收益：

- 可以共享一部分 UI 和设计令牌
- 工程工具链更统一
- 团队前端心智成本更低

CMS 仍然是独立应用，不意味着必须和 `site` 共享运行时边界，只是共享技术生态。

### 为什么 UI 基础选择 `shadcn/ui`

`shadcn/ui` 更适合你当前对 UI 的目标：

- 可以做出更强的品牌化和页面质感
- 组件以源码形式进入项目，可控性高
- 不会被成品组件库的固定视觉语言锁死
- 对内容站和 CMS 都适用

### 为什么 `api` 选择 `NestJS`

内容平台后端会逐步具备明确的领域能力：

- 内容模型和状态流转
- 后台权限与角色能力
- 媒体资源和上传链路
- 发布、下线、审计和检索

这类能力与 `NestJS` 的模块化组织方式是匹配的。

## 备选方案与取舍

### 备选一：`React + Vite + shadcn/ui`

优点：

- 更轻，启动更快
- 适合验证型项目

不推荐作为当前默认方案的原因：

- 站点一旦认真进入 SEO、SSG、文章分发场景，后面大概率还要迁一次框架

### 备选二：继续留在当前 `gaoge` monorepo

优点：

- 前期最快

不推荐原因：

- 与“独立产品线”的前提冲突
- 长期边界会越来越模糊

### 备选三：围绕现成 Headless CMS 做一体化产品

优点：

- 内容建模和编辑能力起步快

不推荐原因：

- 对前台品牌体验、UI 控制力和长期工程边界不够理想

## 最终结论

本次设计确认以下结论：

1. 新媒体平台应新建独立 monorepo，而不是继续放在当前 `gaoge` 仓库内演进
2. 新仓库按完整产品线建设，包含 `apps/site`、`apps/cms`、`apps/api`
3. 共享层包含 `packages/shared`、`packages/sdk`、`packages/ui`
4. 站点与 CMS 的前端统一选择 React 生态
5. `site` 与 `cms` 推荐使用 `Next.js`
6. `api` 推荐使用 `NestJS`
7. UI 基础采用 `shadcn/ui + Tailwind CSS v4`

## 后续需要继续设计的内容

- 新仓库的初始化方式和目录脚手架
- 内容领域模型与发布状态设计
- CMS 信息架构和权限边界
- `site` 的路由与 SEO 策略
- 资源上传、预览与发布链路
- 部署、环境变量与多环境发布流程
