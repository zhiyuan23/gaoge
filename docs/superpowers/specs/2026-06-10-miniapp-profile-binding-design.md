# 小程序我的页面球员绑定方案

> 适用范围：`apps/miniapp`

## 1. 背景与目标

当前 `apps/miniapp` 已经具备微信静默登录、`/miniapp/me` 当前用户查询、可绑定球员列表查询和首次绑定接口，但“我的”页仍然只是一个简单信息占位页，没有形成完整的用户信息展示与绑定闭环。

本方案目标是在 `pages/profile/index` 内完成“我的”页首版能力：

- 展示当前访问小程序用户的个人信息
- 展示当前用户是否已经绑定球员
- 若已绑定，展示对应球员信息
- 若未绑定，在当前页内完成按球员号码选择并绑定
- 绑定成功后立即切换为已绑定展示态

## 2. 范围与非目标

### 2.1 本次范围

- 改造 `apps/miniapp/src/pages/profile/index.vue`
- 在当前页内补齐未绑定态、已绑定态和绑定交互
- 复用现有 `GET /miniapp/me`
- 复用现有 `GET /miniapp/football-player/bind-options`
- 复用现有 `POST /miniapp/football-player/bind`
- 在 `authStore` 中补一个轻量的当前用户信息更新入口，避免页面直接改写 store 内部状态

### 2.2 非目标

- 不新增单独的“绑定球员”页面
- 不实现解绑
- 不实现改绑
- 不改造后端接口协议
- 不扩展到篮球或其他业务身份绑定

## 3. 核心设计决策

### 3.1 绑定流程保留在“我的”页内

未绑定用户在 `pages/profile/index` 当前页内完成绑定，不跳转新页面。

这样处理的原因：

- 和用户确认的交互方向一致
- 改动范围最小
- 不引入新的路由、页面状态同步和回跳问题

### 3.2 当前用户数据以 `authStore.me` 为唯一页面来源

“我的”页不单独维护一份与登录用户相关的缓存数据，页面展示统一从 `authStore.me` 派生。

绑定成功后由页面调用 store 的更新方法写回最新 `me` 结果，页面随即切换到已绑定态。

这样可以避免出现：

- 接口成功但页面状态未刷新
- 页面局部状态与全局登录态不一致
- 重新进入页面后又回到旧展示态

### 3.3 球员查询链路沿用现有 token 语义

页面不额外按 openid 发起独立查询。

当前小程序访问链路已经是：

1. 前端通过 `uni.login` 获取微信 `code`
2. 后端根据 `code` 换取 openid 并建立/定位 `User`
3. 后端签发 token
4. 前端通过 token 访问 `/miniapp/me`
5. 后端根据 token 对应 `user.id` 查询绑定球员

因此“根据 openid 或 token 查询球员信息”的业务目标，在现有实现里已经统一收敛到 token 会话查询，不需要再新增一套 openid 直查接口。

## 4. 页面状态设计

### 4.1 加载态

页面进入时优先执行现有会话恢复逻辑，确保 `authStore.me` 为最新结果。

页面在等待用户信息期间显示基础加载占位，不直接渲染“未绑定”结论，避免闪烁。

### 4.2 已绑定态

当 `me.user.isBound === true` 且 `me.binding` 存在时，页面展示：

- 微信用户信息
  - `openid`
  - 微信昵称
  - 头像占位
- 球员绑定信息
  - `playerNumber`
  - `nickname`
  - `subTeam`
  - `status`

已绑定态不提供解绑或改绑入口。

### 4.3 未绑定态

当 `me.user.isBound === false` 且 `me.binding === null` 时，页面展示：

- 当前微信用户基础信息
- 明确提示“你还没有绑定球员，请先选择球员号码完成绑定”
- 主按钮“绑定球员号码”

未绑定态不展示空的球员信息卡片。

## 5. 绑定交互设计

### 5.1 打开绑定弹层

用户点击“绑定球员号码”后：

1. 请求 `/miniapp/football-player/bind-options`
2. 获取当前尚未被绑定的球员号码列表
3. 在当前页内打开弹层展示列表

弹层不在页面初始加载时预拉数据，避免对已绑定用户产生无意义请求。

### 5.2 弹层内容

弹层内每个选项展示为：

- `#号码`
- `昵称`
- `分队`

展示格式示例：

```text
#7 齐达内 · real
```

用户先点选一个号码，再点“确认绑定”提交。

### 5.3 提交绑定

点击确认后调用：

```text
POST /miniapp/football-player/bind
```

请求体：

```json
{
  "playerNumber": 7
}
```

成功后：

- 关闭弹层
- 用接口返回的最新 `me` 结果更新 `authStore.me`
- 页面立即切换到已绑定态

## 6. 异常与空状态设计

### 6.1 候选列表为空

当 `/miniapp/football-player/bind-options` 返回空列表时，弹层显示“暂无可绑定球员”，不展示确认按钮或禁用确认按钮。

### 6.2 候选列表加载失败

当绑定候选列表请求失败时：

- 页面保持在未绑定态
- 弹层内展示失败提示
- 提供重试入口

### 6.3 未选择号码直接确认

前端先行拦截，提示用户先选择球员号码，不向后端发送空请求。

### 6.4 绑定失败

若后端返回以下语义，前端直接透传提示：

- 当前用户已绑定球员
- 该球员已被绑定
- 未找到对应球员
- 网络异常或其他接口失败

绑定失败后：

- 不清空当前登录态
- 不关闭页面
- 不修改 `authStore.me`

### 6.5 登录态失效

如果 `/miniapp/me` 或绑定接口因 token 失效触发刷新或清理流程，继续交由现有请求层处理。

“我的”页不重复实现一套鉴权失败处理逻辑。

## 7. 代码改动计划

### 7.1 `apps/miniapp/src/pages/profile/index.vue`

新增或调整以下内容：

- 页面加载与刷新逻辑
- 已绑定态与未绑定态 UI
- 绑定按钮
- 当前页内弹层
- 候选列表加载、选择、提交与错误提示

### 7.2 `apps/miniapp/src/store/auth/index.ts`

补一个轻量方法，用于：

- 更新 `me`
- 让页面通过 store 提交最新用户信息

不在页面内直接写 `authStore.me.value`。

### 7.3 其他文件

仅在必要时补最小辅助改动，例如：

- 页面里复用的轻量格式化逻辑
- 与当前交互直接相关的类型引用

后端与共享协议本次默认不改。

## 8. 测试与验证

最低验证标准按 `apps/miniapp` 范围执行：

- `pnpm --filter @gaoge/app-miniapp typecheck`

如果实现过程中补了可运行的前端测试，再追加对应定向测试；若当前 `miniapp` 没有合适的现成测试基建，则以类型检查作为最低验证。

## 9. 验收结果

完成后应满足以下结果：

- 打开“我的”页能看到当前登录用户信息
- 已绑定用户能看到绑定球员信息
- 未绑定用户能在当前页内打开号码选择弹层
- 只能选择后端返回的可绑定号码
- 绑定成功后页面立即切换为已绑定态
- 候选列表为空、加载失败、未选择号码和绑定失败都有明确反馈
