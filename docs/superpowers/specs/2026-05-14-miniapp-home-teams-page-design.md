# 小程序首页球队展示页迁移方案

日期：2026-05-14

## 目标

参考 `apps/web/src/views/TeamsPage.vue` 的内容，在 `apps/miniapp/src/pages/home/index.vue` 落一个完整的小程序版首页，保留现有登录态展示，并补齐球队展示主内容。

本次目标是：

- 在小程序首页保留当前登录态信息
- 迁移 web 端球队展示的核心内容到 miniapp
- 支持足球队与篮球队切换
- 支持足球赛季积分榜展示
- 支持球队图片轮播
- 保持改动范围聚焦在 `apps/miniapp`，不扩大为跨包重构

本次先完成设计，不在本文档中展开实现代码。

## 背景

当前仓库中：

- `apps/web/src/views/TeamsPage.vue` 已经具备完整的球队展示页面，包括 Hero、球队信息、引言、足球积分榜和图片轮播
- `apps/miniapp/src/pages/home/index.vue` 当前仅展示登录态摘要
- 小程序登录态已经由 `useAuthStore().me` 提供，并在 `App.vue` 的 `ensureSession()` 中完成会话恢复
- 后端已提供 `GET /football/standings`，web 端已有对应消费逻辑

因此这次不需要重新设计后端 standings 聚合，也不需要改登录主流程，而是把 web 端已存在的展示能力按小程序交互方式迁入首页。

## 范围

包含：

- 重写 `apps/miniapp/src/pages/home/index.vue`
- 新增 miniapp 侧球队静态数据模块
- 新增 miniapp 侧 standings 请求封装
- 首页保留并整合当前登录态卡片
- 首页支持球队切换、Hero、球队基础信息、引言、积分榜、轮播图

不包含：

- 把球队静态数据上移到 `packages/*`
- 修改 `apps/web` 页面实现
- 修改 `apps/api` standings 接口口径
- 新增小程序独立球队详情页
- 新增后台管理入口或新的导航结构

## 设计结论

### 方案选择

本次不直接复用 `apps/web` 私有模块，也不把共享抽象提前沉到 `packages/*`。

采用方案是：

- 在 `apps/miniapp` 内新增球队展示所需的静态数据与请求封装
- 在首页内完成球队展示 UI 的 uni-app 版本重写
- 保留现有登录态卡片作为首页顶部信息区

原因：

- `apps/*` 之间禁止直接依赖，不能让 miniapp 直接引用 web 私有数据模块
- 当前需求只要求首页落地，提前抽共享会放大改动范围
- 球队展示数据目前仍偏页面展示型，尚不足以证明已经形成稳定共享能力

### 首页结构

首页保持单页结构，不新增页面拆分。页面从上到下分为：

1. `CustomNavbar`
2. 登录态卡片
3. 球队切换栏
4. Hero 区
5. 球队基础信息卡片组
6. 引言区
7. 足球积分榜区块（仅足球队显示）
8. 图片轮播区

这样做的原因是：

- 当前 tabBar 已把首页作为核心入口
- 球队展示与登录态都属于首页信息流的一部分
- 不需要再引入新的小程序路由和页面跳转负担

## 数据与状态设计

### 登录态保留策略

继续复用 `useAuthStore()`：

- `me?.user.isBound`
- `me?.user.openid`
- `me?.binding?.playerNumber`
- `me?.binding?.nickname`

首页不新增登录态副本，不额外缓存派生状态。页面只读消费 store 中已有结果。

### 球队静态数据

在 `apps/miniapp` 内新增独立模块承载：

- 球队列表
- 主题色
- Hero 图
- 图库
- 基础信息
- 引言文案

字段结构保持与 web 端接近，但定义在 miniapp 自己的目录下，避免跨应用依赖。

### 页面本地状态

首页新增本地状态：

- `activeTeam`
- `currentSlide`
- `standingsLoading`
- `standingsError`
- `standings`
- 固定赛季参数 `seasonYear=2026`
- 固定赛段参数 `seasonName='春季赛'`

本期赛季筛选控件不对外开放，先与 web 端当前行为保持一致，仅请求默认赛季。

## API 设计

### standings 请求封装

在 miniapp 侧新增请求方法，请求现有接口：

- `GET /football/standings?year=2026&season=春季赛`

请求层职责：

- 通过 miniapp 现有 `api` / `request` 体系发起请求
- 返回给首页稳定的 standings 数据结构

### 首页加载行为

加载规则如下：

- 默认激活球队为足球队 `gaoge-fc`
- 首页进入时如果当前为足球队，则自动加载 standings
- 切到篮球队时，不请求 standings，并清空积分榜视图状态
- 切回足球队时，重新请求 standings
- 请求失败时展示错误态和重试入口

为避免切换过快导致旧请求覆盖新状态，需要保留请求序号或同等防抖/丢弃机制。

## 界面与交互设计

### 视觉方向

不直接照搬 web 端黑底页面，而是保持小程序当前的浅色卡片体系：

- 页面底色保持浅灰或接近现有首页底色
- 内容主体使用白底卡片
- 球队主色只作为按钮、标题、进度条和强调元素

原因：

- 小程序已有页面与导航是浅色体系
- 直接搬 web 深色视觉会让首页风格断裂
- 本次目标是迁移信息结构与交互，不是做一次跨端视觉完全统一

### 登录态卡片

顶部保留现有登录态展示，并扩展为四行信息：

- 是否已绑定
- `openid`
- 球员号码
- 球员昵称

该卡片始终显示，不因球队切换而变化。

### 球队切换

采用横向双按钮切换：

- 高歌 FC
- 环球港篮球

选中态使用球队主色，未选中态保持中性边框或浅底。

不引入 web 端的悬浮侧边切换器，因为小程序首页更适合顺序流式布局。

### Hero 区

Hero 使用大图卡片：

- 背景图使用球队 Hero 图
- 覆盖渐变遮罩，确保标题可读
- 展示球队名、英文全名和简化标识块

web 端使用 Iconify 图标，小程序端本期不强依赖同一图标方案。若现有小程序图标体系不适合，使用文本徽标或首字母标识块作为稳妥替代。

### 球队基础信息区

使用四张小卡片展示：

- 成立时间
- 城市
- 主场
- 类型

布局优先两列换行，以适配常见手机宽度。

### 引言区

单独一张卡片展示球队引言：

- 标题为“引言”
- 文案内容直接使用球队描述

### 足球积分榜区

仅在 `activeTeam === 'gaoge-fc'` 时渲染。

区块包含三种状态：

- 加载中
- 加载失败
- 空数据 / 正常数据

正常数据下显示两部分：

- 三队积分摘要卡
- 每轮积分明细表

积分摘要卡保留以下信息：

- 队名
- 队伍 code
- 总积分
- 奖杯数（`roundPoints` 中值为 `2` 的次数）
- 积分进度条

明细表做移动端适配：

- 使用横向滚动容器包裹表格
- 列顺序与 standings 数据排序保持一致
- 每轮每队展示积分
- 总积分展示在表尾

### 图片轮播

图片轮播改用 uni-app `swiper`，不保留 web 端手势和 hover 行为。

轮播要求：

- 支持左右滑动
- 支持指示点
- 支持切换当前索引
- 高度固定，图片裁切方式为 `aspectFill`

本期不额外增加自动播放、缩略图导航或全屏预览。

## 错误处理

### standings 失败

当 standings 请求失败时：

- 显示错误文案
- 提供“重试”按钮
- 不影响登录态卡片与球队静态内容展示

### 图片资源问题

若远程图片加载失败，本期不做复杂兜底图片服务，仅接受小程序默认空白态展示或后续补本地兜底图。

不为了这次迁移引入新的图片下载、缓存或代理逻辑。

## 代码组织

建议新增或调整如下位置：

- `apps/miniapp/src/pages/home/index.vue`
- `apps/miniapp/src/data/teams.ts` 或同职责目录
- `apps/miniapp/src/api/football/standing.ts` 或等价位置

要求：

- 页面只组织展示状态与交互
- 球队静态数据不内联在页面大文件底部
- standings 请求走 miniapp 现有 API 分层

## 测试与验证

本次至少验证以下内容：

- `apps/miniapp` 类型检查通过
- 首页能正常读取并展示当前登录态
- 默认显示足球队内容
- 切到篮球队时积分榜隐藏
- 切回足球队时积分榜重新加载
- standings 加载失败时错误态和重试按钮可用
- 轮播图可滑动，指示点与当前图同步

本次不要求补齐端到端自动化测试，但实现时应优先补最小可维护的类型与逻辑校验。

## 实施边界

本次实现必须遵守以下边界：

- 不改动 `apps/web` 现有球队页
- 不新增 `packages/* -> apps/*` 或 `apps/* -> apps/*` 依赖
- 不顺手重构 miniapp 其他页面
- 不借机引入新的全局状态或新的 tabBar 结构

## 结论

本次以“首页完整迁移球队展示 + 保留登录态”为目标，在 `apps/miniapp` 内部独立补齐数据模块、API 封装和 uni-app 页面实现。

这样可以在不扩大 monorepo 共享层改造范围的前提下，快速让小程序首页具备与 web 团队页同等级的信息表达能力，同时保持当前登录态入口不丢失。
