# 小程序微信会员支付方案设计

> 适用范围：高歌体育 monorepo 中 `apps/miniapp` 与 `apps/api` 的微信小程序自营收款场景。

## 1. 背景与目标

当前仓库已完成 `apps/miniapp` 与 `apps/api` 的首轮迁移，并具备微信登录基础能力，但尚未接入面向真实业务的小程序支付能力。

本方案面向 `单一自营收款` 的微信小程序会员年费场景，目标是产出一份可直接指导后续执行的完整方案，覆盖：

- 微信侧前置条件与开通项
- 产品、运营、财务、风控、上线检查项
- `apps/miniapp + apps/api` 的技术接入设计
- 会员订单、支付、退款、对账、状态流转
- 联调、测试、灰度与正式上线清单

## 2. 范围与边界

### 2.1 方案范围

- 小程序前端：
  - 会员商品展示
  - 会员购买
  - 支付拉起
  - 支付结果展示
  - 当前会员状态展示
- 后端：
  - 会员商品读取
  - 会员订单创建与查询
  - 微信支付下单
  - 支付回调处理
  - 退款处理
  - 查单补偿支持
  - 会员权益发放与回收
- 数据库：
  - 会员商品
  - 会员订单
  - 支付流水
  - 退款流水
  - 会员权益

### 2.2 非目标

- 不覆盖服务商、多商家、平台代收款模式
- 不覆盖商城购物车、多商品组合结算
- 不引入优惠券、满减、积分抵扣、邀请返利等营销能力
- 不实现自动续费
- 不先做跨全部业务的通用支付平台

## 3. 核心业务假设

- 用户在小程序内购买年费会员
- 首期按单一会员商品或少量固定套餐处理，优先支持 `年费会员`
- 支付成功后，会员权益由后端确认生效
- 支付最终结果以微信异步通知和后端查单结果为准
- 退款首期按后台人工发起设计，不开放用户端自助退款

## 4. 前置条件与平台开通清单

### 4.1 必须具备的账号与主体

- 已认证的微信小程序账号
- 可用的微信支付商户号
- 小程序 `AppID` 与微信支付商户号已完成绑定
- 主体按自营收款处理，小程序主体与商户主体需满足微信支付的同主体或合规关联要求
- 本方案默认使用普通商户直连模式

### 4.2 必须开通的微信能力

- 微信小程序：
  - 小程序账号认证
  - 正式发布能力
- 微信支付商户平台：
  - JSAPI 支付权限
  - APIv3 接口能力
  - 商户 API 证书与私钥配置能力
  - 支付结果通知能力
  - 退款能力

### 4.3 必须准备的关键配置项

小程序侧：

- `WECHAT_APPID`
- `WECHAT_APPSECRET`

微信支付侧：

- `WECHAT_PAY_MCHID`
- `WECHAT_PAY_APPID`
- `WECHAT_PAY_API_V3_KEY`
- `WECHAT_PAY_SERIAL_NO`
- `WECHAT_PAY_PRIVATE_KEY`
- `WECHAT_PAY_NOTIFY_URL`
- `WECHAT_PAY_REFUND_NOTIFY_URL`

服务器侧：

- 可公网访问的正式回调地址
- HTTPS 能力
- 可安全存储密钥的环境变量或部署配置体系

### 4.4 运营与财务前置准备

- 明确会员商品：
  - 名称
  - 售价
  - 有效期
  - 是否支持续费
  - 是否支持退款
  - 退款规则
- 明确页面文案：
  - 商品标题
  - 商品说明
  - 购买须知
  - 用户协议
  - 隐私政策
  - 会员服务协议
- 明确会员权益：
  - 支付成功后何时生效
  - 续费是否顺延叠加
  - 退款后权益何时失效
- 明确财务流程：
  - 对账负责人
  - 退款审批流程
  - 购买凭证策略
  - 异常订单处理责任人

### 4.5 上线前硬性检查项

- 小程序已认证并具备发布能力
- 商户号已开通 JSAPI 支付
- `AppID` 与商户号已绑定
- APIv3 密钥、私钥、证书序列号已正确配置
- 支付与退款回调地址可被微信支付访问
- 已完成正式环境真机联调
- 已建立异常订单排查与人工补单流程

## 5. 业务方案与状态流转

### 5.1 会员商品方案

- 首期按固定会员商品处理，不做复杂商品中心
- 推荐首期只提供一个主商品：`年费会员`
- 若业务确有需要，可扩展到少量固定套餐：
  - `月卡`
  - `季卡`
  - `年卡`

### 5.2 会员权益生效规则

- 首次购买：
  - `startAt = 支付确认时间`
  - `endAt = startAt + durationDays`
- 续费购买：
  - 若当前仍在会员有效期内，新的权益时长按当前 `endAt` 顺延叠加
  - 若当前会员已过期，从新的支付确认时间重新计算

### 5.3 核心模型拆分

支付方案至少拆分为以下四类记录：

- `会员订单`
- `支付流水`
- `退款流水`
- `会员权益记录`

拆分原因：

- 一笔会员订单可能经历多次支付尝试
- 一笔已支付订单可能发生退款
- 会员权益的实际生效区间不能直接等同于订单支付时间字段

### 5.4 会员订单状态

推荐状态：

- `pending`
- `paid`
- `closed`
- `refund_pending`
- `refunded`
- `refund_failed`

### 5.5 支付流水状态

推荐状态：

- `created`
- `success`
- `failed`
- `cancelled`

### 5.6 退款流水状态

推荐状态：

- `pending`
- `success`
- `failed`
- `closed`

### 5.7 关键业务规则

- 同一用户可重复购买年费会员，续费按顺延叠加处理
- 未支付订单允许关闭
- 同一笔已支付订单不能再次支付
- 支付成功后的会员权益发放必须幂等
- 退款成功后的权益回收需按规则处理
- 已发生续费叠加的历史订单退款，首期默认人工审核

## 6. 技术架构方案

### 6.1 总体原则

- 支付方案只落在 `apps/miniapp` 与 `apps/api`
- 遵守 monorepo 现有依赖方向，不新增应用间直接依赖
- 首期不抽全业务支付平台，只做：
  - 通用微信支付能力
  - 会员年费业务接入
- 所有支付真实性判断、会员发放、退款、查单放在后端

### 6.2 后端模块拆分建议

推荐在 `apps/api/src` 新增：

- `common/wechat-pay/`
  - `wechat-pay.module.ts`
  - `wechat-pay.service.ts`
  - `wechat-pay.types.ts`
  - `wechat-pay.util.ts`
  - 职责：微信支付 V3 调用、回调验签、查单、退款、调起支付参数生成
- `modules/member/`
  - 职责：会员商品读取、当前会员状态查询、会员权益发放与回收
- `modules/member-order/`
  - 职责：会员订单创建、查询、关闭
- `modules/member-payment/`
  - 职责：发起支付、接收支付回调、发起退款、接收退款回调、补偿查单

### 6.3 小程序端结构建议

推荐在 `apps/miniapp/src` 增加：

- `api/member/`
  - `getProducts`
  - `getCurrentMemberStatus`
- `api/member-order/`
  - `createMemberOrder`
  - `getMemberOrderDetail`
- `api/member-payment/`
  - `createMemberPayParams`
- `pages/member/`
  - 会员商品页与购买入口
- `pages/member/pay-result/`
  - 支付结果页

### 6.4 登录态收敛要求

当前 `apps/miniapp` 仍保留 `thirdSessionKey` 旧约定，而 `apps/api` 已提供 JWT 登录体系。

支付接入前需要先统一为：

- 小程序登录后保存 `accessToken/refreshToken`
- 请求头统一改为 `Authorization: Bearer <accessToken>`
- 支付相关接口不再依赖 `thirdSessionKey`

原因：

- 避免支付链路继续沿用旧会话逻辑
- 减少未来订单、支付、会员状态接口的鉴权分裂

## 7. 接口设计与前后端数据流

### 7.1 认证前提

除微信支付回调接口外，所有会员、订单、支付接口默认要求用户已登录，并使用 JWT 鉴权。

### 7.2 会员与状态接口

- `GET /member/products`
  - 返回当前可购买的会员商品列表
- `GET /member/current`
  - 返回当前登录用户的会员状态

### 7.3 会员订单接口

- `POST /member-orders`
  - 根据 `productCode` 创建待支付订单
- `GET /member-orders/:id`
  - 查询订单详情与最新状态
- `GET /member-orders`
  - 查询当前用户的会员订单列表
- `POST /member-orders/:id/close`
  - 关闭当前用户自己的 `pending` 订单

### 7.4 支付接口

- `POST /member-payments/:orderId/pay`
  - 为指定待支付订单生成微信小程序支付参数
- `POST /member-payments/wechat/notify`
  - 接收微信支付结果通知

### 7.5 退款接口

- `POST /member-refunds`
  - 后台或内部运营发起退款
- `POST /member-payments/wechat/refund-notify`
  - 接收微信退款通知

### 7.6 标准成功链路

1. 小程序获取会员商品与当前会员状态
2. 用户选择商品并创建会员订单
3. 小程序请求支付参数
4. 后端向微信支付统一下单并返回调起参数
5. 小程序调用 `uni.requestPayment`
6. 微信完成扣款
7. 微信异步通知后端支付结果
8. 后端更新支付流水、订单状态与会员权益
9. 小程序支付结果页刷新订单与会员状态

### 7.7 异常链路原则

- 用户取消支付：
  - 前端提示取消
  - 订单仍可保持 `pending`
- 前端提示失败但微信实际成功：
  - 由异步通知或查单结果修正
- 回调丢失：
  - 由补偿查单修正
- 权益发放失败：
  - 必须记录异常并支持人工补偿

## 8. 数据表与状态字段设计建议

### 8.1 设计原则

- 首期只建设支撑会员年费支付所需的最小模型

- 状态字段使用明确枚举值

- 当前会员状态通过 `MemberEntitlement` 聚合得到

- `MemberProduct`
  - `code` 唯一索引

  - `orderNo` 唯一索引
  - `userId + createdAt` 普通索引
  - `status` 普通索引

  - `outTradeNo` 唯一索引
  - `transactionId` 唯一索引

## 9. 支付、回调、退款与补偿机制

### 9.1 支付发起原则

- 支付参数只能由后端生成
- 前端不能自行决定金额、商品标题、`openid`
- 发起支付前，后端必须校验：
  - 当前用户存在有效 `openid`
  - 订单属于当前用户
  - 订单状态为 `pending`
  - 商品仍可售
  - 订单金额与商品快照一致

### 9.2 调起支付流程

后端：

1. 校验订单
2. 生成 `outTradeNo`
3. 调微信支付统一下单接口
4. 保存 `MemberPayment`
5. 返回小程序支付参数

前端：

1. 获取支付参数
2. 调用 `uni.requestPayment`
3. 展示支付成功、取消或失败提示
4. 刷新订单详情与会员状态

### 9.3 支付回调处理原则

后端处理微信支付回调时必须：

1. 验签、解密、校验商户号、`appid`、交易状态
2. 根据 `out_trade_no` 找到本地支付流水与订单
3. 校验本地金额与通知金额一致
4. 幂等更新：
   - `MemberPayment = success`
   - `MemberOrder = paid`
   - 生成或更新 `MemberEntitlement`
5. 仅在本地处理成功后返回微信成功应答

### 9.4 会员权益发放规则

- 若当前存在未过期权益：
  - 新权益 `startAt = 当前权益 endAt`
  - 新权益 `endAt = 当前权益 endAt + durationDays`
- 若当前不存在有效权益：
  - 新权益 `startAt = 支付确认时间`
  - 新权益 `endAt = 支付确认时间 + durationDays`

幂等要求：

- 同一订单只能发放一次权益
- 重复回调不能重复新增权益区间

### 9.5 退款处理原则

首期退款按后台人工发起设计。

退款流程：

1. 校验订单是否允许退款
2. 校验是否存在进行中的退款流水
3. 生成 `refundNo`
4. 调微信退款接口
5. 创建 `MemberRefund = pending`
6. 更新 `MemberOrder = refund_pending`

退款回调到达后：

1. 验签并解密通知
2. 定位退款流水与订单
3. 幂等更新退款流水
4. 更新订单状态
5. 回收会员权益或转人工处理

### 9.6 会员权益回收建议

- 若退款订单带来的权益尚未被后续续费叠加覆盖：
  - 将对应权益标记为 `revoked`
  - 或按规则缩短为合理时段
- 若该订单之后已存在新的续费叠加：
  - 首期不自动重算整条权益链
  - 转人工审核处理

### 9.7 查单补偿机制

建议至少支持以下补偿场景：

- `pending` 订单超时未落账
- 前端提示失败但用户反馈已扣款
- 支付流水长期停留在 `created`

补偿策略：

- 定时或人工触发查单
- 若微信侧成功、本地未成功：
  - 按支付成功流程补写订单、流水、权益
- 若微信侧明确未支付或已关闭：
  - 关闭本地订单或标记人工处理

### 9.8 超时与关闭策略

- `pending` 订单不应无限保留
- 建议业务超时设置为 `15 ~ 30 分钟`
- 超时订单可在再次购买前优先关闭
- 对临界时间订单，关闭前或关闭后应做一次查单确认

### 9.9 日志要求

至少记录：

- 下单请求参数摘要
- 微信接口响应摘要
- 回调接收时间
- 核心状态变更前后
- 退款请求与退款通知
- 权益发放与回收结果
- 补偿查单结果

禁止明文打印：

- 私钥
- APIv3 密钥
- 完整敏感身份数据

## 10. 运营、财务、风控与上线检查

### 10.1 产品与运营必须明确的规则

- 会员名称、售价、有效期、续费规则、退款规则
- 支付成功后的生效时间
- 已有会员续费时的顺延规则
- 退款后的权益失效规则
- 商品介绍、购买须知、协议文案

### 10.2 财务侧必须准备的流程

- 明确商户号归属与结算账户
- 明确对账、退款审批、异常订单核对责任人
- 明确购买凭证策略
- 明确对账口径：
  - 微信支付成功笔数
  - 本地成功订单笔数
  - 实际发放会员权益笔数
  - 退款金额与退款笔数

### 10.3 风控与投诉风险点

重点风险：

- 用户付款后前端未及时显示成功
- 续费叠加规则认知不一致
- 退款规则模糊
- 商品描述与实际权益不一致
- 异常订单缺乏人工补偿流程

上线前需明确：

- 支付成功结果页文案
- 会员生效时间说明
- 到期时间说明
- 退款说明
- 用户咨询入口

### 10.4 正式上线配置检查

小程序侧：

- `AppID` 正确
- 正式版可发布
- 协议链接可访问

后端侧：

- 正式环境域名可访问
- 支付回调地址使用正式 HTTPS 域名
- 小程序与微信支付全部环境变量已正确配置

商户平台侧：

- JSAPI 支付权限已开通
- 小程序 `AppID` 已绑定商户号
- APIv3 密钥已设置
- 商户证书与序列号匹配

数据侧：

- 会员商品已初始化
- 测试订单数据已清理或隔离
- 日志与异常记录可查看

### 10.5 联调与验收测试清单

至少覆盖：

- 正常购买年费会员
- 已是会员时再次续费并正确顺延
- 用户取消支付
- 支付失败
- 支付成功但结果页进入失败后可恢复
- 微信回调重复通知
- 支付成功但本地处理异常，可人工补偿
- 后台发起全额退款
- 退款成功后权益正确回收
- 已发生续费叠加的历史订单退款进入人工处理
- 超时未支付订单关闭
- 用户订单列表正确显示状态

### 10.6 灰度与正式发布建议

建议节奏：

1. 开发环境联调
2. 测试环境验证
3. 正式环境少量真实账号灰度
4. 核对真实支付、回调、退款、权益发放、日志
5. 再逐步全量开放

若暂时没有灰度体系，至少先只让内部测试账号看到会员购买入口。

### 10.7 上线初期值守建议

- 指定异常日志查看人
- 指定“扣款未到账”反馈处理人
- 指定退款审核人
- 指定与财务核对首批订单的人

## 11. 实施顺序、里程碑与验收标准

### 11.1 实施总原则

- 先打通支付闭环，再补后台管理与自动补偿能力
- 先完成单一会员年费商品，再考虑多套餐
- 先完成人工可处理的最小退款方案
- 先统一 `miniapp` 登录态到 JWT，再接支付

### 11.2 推荐实施顺序

阶段 0：前置准备

- 完成资质、商户、配置、商品规则准备

阶段 1：登录态与配置收敛

- 小程序统一使用 `Authorization: Bearer <accessToken>`

阶段 2：会员商品与会员状态只读能力

- 商品列表、当前会员状态可读

阶段 3：订单创建与支付拉起

- 创建订单、生成支付参数、调起微信支付

阶段 4：支付回调与会员权益发放

- 完成支付成功后的落账与权益发放闭环

阶段 5：退款与权益回收

- 支持后台人工发起全额退款与简单权益回收

阶段 6：异常补偿、联调收口与上线准备

- 增加查单补偿、异常处理、灰度和值守准备

### 11.3 里程碑建议

- `M1：前置条件完成`
- `M2：支付发起跑通`
- `M3：支付闭环完成`
- `M4：上线可控`

### 11.4 正式上线验收标准

只有同时满足以下条件，才建议进入正式上线：

- 支付主链路已通过真实环境验证
- 续费顺延规则已验证
- 支付重复通知已验证幂等
- 退款链路已验证
- 异常订单可定位、可补偿、可人工处理
- 运营与财务对规则和处理流程无歧义
- 用户端文案、协议、说明页已上线

### 11.5 首期明确不纳入验收范围

- 自动续费
- 多会员套餐复杂组合
- 用户自助退款
- 自动化全量对账系统
- 完整后台会员运营中心
- 多端统一会员体系扩展

### 11.6 上线后第一轮观察指标

- 支付成功率
- 支付成功但本地未及时落账数量
- 回调重复率
- 退款成功率
- 用户投诉量
- 人工补单次数
- 会员生效异常次数

## 12. 当前仓库现状与本方案的直接影响

### 12.1 已有基础

- `apps/api` 已具备微信登录基础能力
- `apps/api` 已具备 JWT 登录体系
- `apps/miniapp` 已具备基础请求封装与用户登录流程
- 当前仓库使用 `Prisma + PostgreSQL`

### 12.2 需要优先修正的现状问题

- `apps/miniapp` 请求层仍保留 `thirdSessionKey` 旧约定
- 支付接入前需要统一为 JWT 鉴权
- 仓库中尚未存在会员、订单、支付、退款、权益相关数据模型
- 仓库中尚未存在微信支付 V3 的公共封装模块

### 12.3 设计结论

本方案不建议先做“支付平台化重构”，而是采用：

- `common/wechat-pay` 负责微信支付通用能力
- `member`、`member-order`、`member-payment` 负责会员年费业务落地

这样既能符合当前 monorepo 的目录职责，也能控制首期范围，避免为未来可能出现的业务提前做重型抽象。
