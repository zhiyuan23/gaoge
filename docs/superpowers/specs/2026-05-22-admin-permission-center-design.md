# Admin 权限中心重设计

## 背景

当前 `apps/admin` 已经具备一轮可运行的 RBAC 基础：

- 前端已有 `用户管理 / 角色管理 / 菜单管理 / 权限管理` 四个模块
- 后端已有 `Role / Permission / Menu / UserRole / RolePermission / MenuPermission` 数据模型
- 前端页面和按钮已稳定依赖 `meta.auth`、`v-auth` 和权限码字符串
- 后台用户已开始从单 `role` 字段迁移到多角色绑定

但当前权限功能仍然更像“把四张表做成四个管理页”，而不是一套围绕管理员日常授权任务设计的权限中心。主要问题是：

- 授权主线分散在 `用户 / 角色 / 菜单 / 权限` 四页之间
- `角色管理` 仍是列表页思维，无法承担“角色模板中心”的职责
- 菜单、页面访问、按钮动作、接口动作之间的关系在产品层表达不够清晰
- 技术管理员维护角色模板、比较差异、评估影响面、排查权限来源时成本偏高

本次设计目标不是继续增强旧四页，而是重做一套更通用、更友好的 `apps/admin` 权限中心。

## 目标

- 只服务当前 `apps/admin` 后台，不扩到 `web / miniapp / desktop`
- 主要服务技术型管理员，允许展示底层权限结构和来源链路
- 首期覆盖 `页面访问 + 按钮动作 + 接口动作`
- 用户严格只通过角色授权，不支持用户级直配权限
- 让“维护角色能力模板”成为权限系统的主流程
- 保留菜单独立管理能力，但菜单不再主导授权主线
- 保留系统预置权限，并允许少量受控扩展权限
- 保持当前前后端统一消费权限码的模式，不推翻 `meta.auth` / `v-auth`

## 非目标

- 不做数据范围权限
- 不做多组织、多租户、多应用统一权限平台
- 不做任意数据库配置即自动生成前端页面
- 不做完全脱离代码白名单的动态路由系统
- 不做用户级加权限 / 减权限例外逻辑
- 不重写整套后台 UI 框架，只重组系统管理权限模块

## 已确认的产品约束

- 设计范围：整套权限中心，而不是局部页面优化
- 目标用户：技术型管理员
- 作用范围：仅当前 `apps/admin`
- 权限边界：页面、按钮、接口动作
- 授权原则：只通过角色授权
- 高频场景：维护角色能力模板
- 权限来源：系统预置 + 少量扩展权限
- 菜单定位：独立管理

## 方案对比

### 方案 A：四页并列增强版

保留 `用户 / 角色 / 菜单 / 权限` 四页平权并列，只分别增强列表、筛选、批量操作和弹窗体验。

优点：

- 最贴近当前代码结构
- 改造风险最低
- 迁移成本低

缺点：

- 授权主线仍然分散
- 高频任务“维护角色模板”不够突出
- 本质上仍是旧后台增强，不是新权限中心

### 方案 B：角色中心驱动版

把 `角色` 升级为权限中心主入口，用户、菜单、权限都围绕角色模板展开。默认主线为：

`定义角色能力 -> 配置菜单和动作 -> 分配给用户`

优点：

- 最符合“通用、友好”的目标
- 角色成为稳定授权模板，符合 RBAC 核心模型
- 能把权限继承链、影响面和差异对比放到中心位置

缺点：

- 信息架构改动最大
- 需要重新定义四个模块的关系
- 首期设计和实现复杂度高于纯增强

### 方案 C：资源矩阵配置版

以 `模块 / 资源 / 动作` 为核心矩阵配置能力，角色只是能力组合的承载体。

优点：

- 结构最通用
- 能力边界最清楚
- 有利于未来更多业务模块接入

缺点：

- 配置感过强，产品主线偏弱
- 日常维护角色模板不够顺手
- 容易变成复杂权限面板

## 设计结论

采用 `方案 B：角色中心驱动版`。

原因：

- 当前最重要的不是“把四张表都能改”，而是把授权主线收束到一个稳定模型
- 角色是当前后台里最自然、最稳定、最可复用的能力模板
- 菜单和权限都应该为角色服务，而不是继续与角色平权争夺主流程

## 信息架构

新权限中心仍保留 `用户 / 角色 / 菜单 / 权限` 四个模块，但不再平权并列。

### 1. 角色中心

角色中心是新的主入口，也是默认 landing page。它负责：

- 定义角色基本信息
- 配置角色可访问菜单
- 配置角色可执行动作权限
- 查看当前角色影响到的用户
- 对比角色差异
- 评估变更影响面

角色中心是唯一真正的授权工作台。

### 2. 用户管理

用户管理降级为“角色挂载中心”，不再作为权限设计主入口。它负责：

- 查找用户
- 查看用户当前角色
- 批量分配角色 / 替换角色
- 查看用户权限来源解释

用户页不再直接承担拼装权限职责。

### 3. 菜单管理

菜单管理继续独立存在，但职责收敛为：

- 维护菜单树和页面入口元数据
- 维护显隐、排序、状态、路径、路由名
- 声明菜单入口访问要求
- 给角色中心提供可选菜单树

菜单页不再承担授权主流程。

### 4. 权限字典

权限字典继续独立存在，但定位改成“系统能力仓库”。它负责：

- 管理系统预置权限
- 管理少量扩展权限
- 展示权限元信息、状态和引用关系

权限页不是高频授权页，而是能力定义页。

## 角色中心页面设计

角色中心从当前“角色列表 + 分配权限弹窗”升级为两栏工作台。

### 左栏：角色列表

字段建议：

- 角色名称
- 角色编码
- 状态
- 内置 / 自定义
- 用户数
- 菜单数
- 权限数

能力建议：

- 搜索
- 状态筛选
- 内置 / 自定义筛选
- 快速创建
- 复制角色

左栏的高频动作是切换当前角色，不是频繁打开弹窗。

### 右栏：角色详情工作区

选中一个角色后，右栏展示完整工作区，但授权区不再拆成两个互相独立的大面板，而是改成统一的“访问与动作”工作区。整体分成三块：

- 基本信息
- 访问与动作
- 关联用户

#### 基本信息

字段：

- 名称
- 编码
- 描述
- 状态
- 排序
- 是否内置

#### 访问与动作

授权工作区采用一棵可操作的“访问与动作权限树”，不再拆成左侧菜单树和右侧动作面板两个分离区域。

树结构规则如下：

- `目录` 节点：只负责组织层级，不展示动作权限
- `菜单` 节点：展示菜单访问勾选
- 已勾选的 `菜单` 节点：在节点下方直接内联展开该菜单的动作复选项
- 未勾选的 `菜单` 节点：不展开动作区

它表达的是一条完整主线：

`先勾可访问菜单 -> 直接在该菜单下勾可执行动作`

用户不需要在两个面板之间来回切视线，就能完成一次完整授权。

#### 关联用户

关联用户保留，但降为工作区底部摘要区，只承担影响面感知：

- 展示绑定用户总数
- 展示少量用户摘要
- 提供“前往用户管理”入口

它不再与授权区抢主空间。

### 交互原则

- 角色切换即预览，不再依赖进入弹窗才看详情
- 基本信息独立保存；授权树里的菜单访问和菜单子动作统一一次保存
- 新建角色优先走快速建角色流程
- 深度调角色在右栏工作区内完成
- 内置角色允许查看，但部分字段和删除操作受限

### 授权区状态规则

#### 1. 菜单勾选是子动作前提

- 只有被授权访问的菜单，才允许配置该菜单下的动作权限
- 未勾选菜单时，不展开该菜单下的动作区
- 取消某菜单勾选时，立即清空该菜单下已选动作，避免出现“动作有权限但入口不可达”的脏状态

#### 2. 菜单子动作就地展开

- 动作复选项直接渲染在对应菜单节点下方
- 展示上继续按 `资源 / action` 做小分组，但不再拉出第二个大面板
- 如果某菜单没有挂任何动作权限，节点下显示轻量空态提示

#### 3. 目录节点不挂动作

- `目录` 节点只负责层级组织和折叠展开
- 只有最终可访问的 `菜单` 节点才展示动作权限
- 避免树在高层目录上继续叠加动作配置，造成视觉失控

#### 4. 不展示全局动作权限

- 本期角色中心不再单独展示不挂菜单的全局动作权限
- 产品主流程只围绕“菜单入口 + 菜单内动作”展开
- 若后端仍存在少量不挂菜单的权限，首期不在角色中心主工作区暴露

## 菜单与权限的产品定位

### 菜单不是权限本体

菜单是系统入口和导航结构，不是能力本身。菜单主要回答：

- 系统里有哪些入口
- 某角色能看到哪些入口

但菜单不直接回答“进入后能做什么”。

### 权限项才是能力单位

真正的授权判断应继续以权限码为准。权限项主要回答：

- 是否可以访问某页面
- 是否可以点击某按钮
- 是否可以执行某接口动作

因此角色中心里必须同时配置：

- 可访问入口
- 可执行动作

而不是只配置菜单或只配置一串权限码。

### 菜单与动作的关系

虽然底层仍然统一存储在角色权限集合里，但产品表达上需要明确区分：

- 菜单访问负责决定“这个角色能否进入某入口”
- 菜单子动作负责决定“进入该入口后能否执行某按钮或接口动作”

因此本期不再采用“菜单树 + 右侧动作面板”的双区联动，而是直接把两层权限合并进同一棵授权树里，围绕每个菜单节点就地维护。

## 权限模型分层

本期建议把权限模型拆成两层：

### 1. 入口层

负责决定“能看到 / 进入哪里”。

包含：

- 菜单入口
- 页面访问权限

其中：

- 菜单树用于导航显隐和入口组织
- 页面访问仍继续使用 `*.view` 类权限码作为真正的路由准入判断

### 2. 动作层

负责决定“进入后能做什么”。

包含：

- 按钮动作
- 接口动作

按钮和接口动作在产品概念上不分开，统一视为“动作能力”。

例如：

- `football.assetRecord.create`
- `football.assetRecord.update`
- `football.assetRecord.delete`
- `system.user.reset-password`
- `system.role.assign-permission`

前端按钮显隐与后端接口守卫继续共享同一套权限码。

## 权限分组规则

权限分组采用固定三段式：

`module.resource.action`

例如：

- `system.user.view`
- `system.role.assign-permission`
- `football.assetRecord.update`

在角色中心的呈现方式上，应按：

- 模块
- 资源
- 动作

三级结构组织，而不是裸权限码列表。

示例：

- 系统管理
  - 用户
    - 查看
    - 新增
    - 编辑
    - 启用
    - 停用
    - 重置密码
    - 删除
  - 角色
    - 查看
    - 新增
    - 编辑
    - 分配权限
    - 删除
- 足球管理
  - 资产流水
    - 查看
    - 新增
    - 编辑
    - 删除

### 关于 `view`

`view` 是页面访问的基线能力。

规则建议：

- 页面访问必须显式依赖 `*.view`
- 其他动作权限默认建立在 `view` 之上
- 产品上可做联动提示，但数据上仍显式存储所有动作权限

不做隐式推导，避免隐藏规则导致排查困难。

## 菜单管理设计

菜单管理保留独立模块，负责：

- 菜单树 CRUD
- 标题、图标、路径、路由名、排序、显隐、状态维护
- 入口访问要求声明
- 给角色中心提供菜单树来源

菜单管理不负责：

- 直接成为主授权页
- 动态生成任意前端页面
- 脱离前端代码白名单接管完整运行时路由

菜单管理更像“入口底座管理”。

## 权限字典设计

权限字典保留独立模块，分两类权限：

### 1. 系统预置权限

来自代码里的稳定能力定义，是主流权限来源。

特点：

- 受代码白名单控制
- 支持同步或校验
- 不鼓励后台日常修改 code

### 2. 扩展权限

允许技术管理员在后台新增少量能力项，用于承接未预置但确有接入需要的动作能力。

限制：

- 必须遵守统一命名规则
- 不能制造前后端都未接入的“假能力”
- 应能看到是否被菜单引用、是否被角色引用

### 字段建议

- code
- name
- module
- resource
- action
- description
- status
- isBuiltIn
- 引用信息

权限字典页的重点不是“多快新增”，而是让能力定义保持清晰、稳定、可追踪。

## 用户管理设计

用户管理在新方案中的职责是“把角色落到人”。

核心能力建议：

- 搜索和筛选用户
- 查看用户当前角色
- 批量追加角色
- 批量替换角色
- 查看权限来源解释

用户管理不再提供“直接点权限树给用户授权”的能力。

### 权限来源解释

因为本期坚持“只通过角色授权”，所以用户页必须提供可解释性。

至少应支持：

- 当前用户绑定了哪些角色
- 每个角色分别带来哪些菜单和动作能力
- 某个页面 / 某个动作为什么可做或不可做

这能显著降低权限排查成本。

## 关键交互

为了让这套权限中心真正友好，首期应把以下交互做成一等能力。

### 1. 角色复制

新建角色时允许从现有角色复制，再做少量修改。维护角色模板的常见操作不是从零搭建，而是基于已有模板派生。

### 2. 角色差异对比

允许对比两个角色的：

- 菜单差异
- 权限差异
- 关联用户差异

避免管理员肉眼比对大量勾选项。

### 3. 影响面提示

调整角色前明确提示：

- 当前角色绑定了多少用户
- 移除某菜单或某动作后会影响哪些访问能力

降低误改风险。

### 4. 权限来源解释

在用户侧展示“该用户为什么有这些权限”，并把来源链路收束为：

`用户 -> 角色 -> 菜单 / 权限`

### 5. 为什么不能做

当管理员排查某用户无法执行动作时，至少要能看到：

- 缺少哪个权限码
- 该权限当前属于哪些角色
- 该用户当前绑定了哪些角色

### 6. 批量挂角色

用户管理支持批量追加或替换角色，不要求逐个用户进入编辑弹窗。

### 7. 引用保护

删除或停用前明确给出引用关系：

- 删除角色前提示是否仍有用户绑定
- 删除权限前提示是否仍被角色或菜单引用
- 删除菜单前提示是否仍有子菜单或被角色依赖

## 前后端落地原则

### 1. 角色是唯一授权模板

所有授权维护动作都围绕角色展开。

### 2. 权限码是唯一真实能力标识

前端页面、按钮和后端接口继续共享同一套 code。

### 3. 菜单是入口，不是能力本体

菜单只负责组织入口和导航，不替代真正的动作授权。

### 4. 预置优先，扩展受控

系统预置权限是主流来源；扩展权限允许存在，但必须遵守命名和接入边界。

### 5. 产品主线优先于表主线

管理员在产品里看到的是：

- 角色模板
- 可访问入口
- 可执行动作
- 关联用户

而不是先理解四张表再自己拼授权流程。

### 6. 授权区一次提交

角色中心的授权区应把以下内容视为同一批变更：

- 菜单访问
- 当前各菜单下的动作权限

不再通过两个独立保存动作制造中间态。

### 7. 取消入口即取消子动作

一旦入口被取消，依附于该入口的动作权限必须同步失效并清空，不保留悬空动作勾选。

## 接口与数据形态建议

为支撑“树内联展开式”的授权工作区，角色中心建议返回以下结构：

- `menuTree`
- `menuPermissionGroups: Record<menuId, PermissionModule[]>`
- `relatedUsers`

其中：

- `menuTree` 提供入口层结构和勾选状态
- `menuPermissionGroups` 提供每个菜单节点下可就地展开的动作权限

角色中心保存时，建议统一提交：

- `menuIds`
- `menuPermissionIdsByMenu`

服务端基于这两部分统一生成角色最终权限集合，避免：

- 先保存菜单成功、再保存动作失败
- 菜单变更后残留旧动作权限
- 菜单和子动作之间出现悬空勾选关系

现有分开的 `updateMenuAccess` 和 `updatePermissions` 可以暂时保留，用于兼容旧页面或回滚，但角色中心主流程应切换到统一保存接口。

## 测试重点补充

围绕新的授权区交互，至少补以下验证：

- 取消菜单勾选时，该菜单下已选动作会被清空
- 菜单节点勾选后会在节点下内联展开对应动作区
- 只有 `菜单` 节点展示动作权限，`目录` 节点不展示
- 一次保存会正确合并菜单入口权限和菜单子动作权限

## 与当前实现的关系

本设计不是推翻当前 RBAC 基础，而是在其上重构信息架构和交互主线。

可保留的基础包括：

- 后端已有 `Role / Permission / Menu` 数据模型
- 前端已有 `meta.auth`、`v-auth` 和权限码使用方式
- 当前 `用户 / 角色 / 菜单 / 权限` 四个路由入口

需要重点重构的部分包括：

- `角色管理` 页面形态
- 菜单、权限、用户三页与角色中心的关系
- 权限选择器的组织方式
- 权限来源解释和角色差异对比能力

## 首期落地范围

首期必须做：

- 角色中心工作台
- 菜单入口与动作权限分层表达
- 用户仅通过角色授权
- 菜单管理与权限字典的重新定位
- 角色复制
- 基础权限来源解释
- 基础影响面提示

首期可延后：

- 更复杂的角色差异视图
- 更完整的“为什么不能做”诊断面板
- 更高级的批量授权操作历史

## 验收标准

如果本设计落地成功，应满足以下结果：

- 管理员维护角色模板时不需要反复跳转四个模块拼流程
- 用户授权操作收敛为“给用户挂角色”
- 菜单访问、页面访问、动作能力三者关系清晰
- 前后端仍共享统一权限码，不出现 UI 和 API 双轨权限体系
- 技术管理员能快速解释某用户为什么有或没有某项能力
- 扩展权限存在但不破坏代码白名单和稳定命名体系

## 结论

当前 `apps/admin` 更适合从“四页平权管理”升级为“角色中心驱动的权限工作台”。

这套设计既保留了当前仓库已经落地的 RBAC 基础，又把授权主线重新组织为技术管理员真正高频、可理解、可维护的产品路径。对当前阶段而言，这是在通用性、友好度和实施风险之间最平衡的方案。
