# miniapp 截图对齐 UI 壳与滚动交互方案

日期：2026-06-18

## 1. 目标

为 `apps/miniapp` 建立一套面向微信小程序端的高保真前台 UI 壳，并优先落地到 3 个页面：

- `src/pages/home/index.vue`
- `src/pages/discover/index.vue`
- `src/pages/profile/index.vue`

本次目标是严格对齐用户提供的参考截图与交互节奏：

- 沉浸式顶部视觉
- 自定义导航栏
- 自定义底部 tabBar
- 页面上滚后的导航栏压缩与吸顶变化
- 3 个页面的静态 mock 壳与视觉层级

本次不是业务联调，也不是跨端视觉统一。

## 2. 背景

当前 `apps/miniapp` 已具备：

- `uni-app + Vue 3` 运行基础
- `UnoCSS + 局部 SCSS` 样式能力
- 微信小程序端编译链路
- 已存在的自定义导航栏基础组件 `src/components/base/CustomNavbar.vue`

当前问题是：

- 目标页仍在使用系统导航栏配置，未进入截图所需的自绘导航模式
- 当前底部仍是原生 `tabBar`，无法实现中间凸起绿色加号和整体白底浮层
- `home`、`discover`、`profile` 三页没有统一的滚动联动壳层
- 当前 `home` 和 `discover` 页面内容与截图差距较大，`profile` 页面虽有内容，但不是截图中的个人主页结构

因此，这次需要先把微信端的页面壳和交互壳定下来，再进入真实数据接入。

## 3. 已确认设计 Brief

### 3.1 交付目标

第一阶段只做 `A` 档：

- 仅做 3 个页面的高保真 UI 壳
- 仅做滚动联动和导航过渡
- 使用静态 mock 数据
- 不接真实业务接口

### 3.2 平台边界

本次设计只要求微信小程序端对齐截图。

不要求：

- `H5` 对齐同等视觉
- 其他小程序端对齐同等视觉
- App 端或桌面端复用这套壳

非微信端只要求保持基础可编译或可退化，不作为本次验收目标。

### 3.3 参考来源

参考对象为用户提供的“粗来”小程序截图。

由于未获取到稳定可复用的公开设计资源，本次以截图高保真复刻为准，不等待额外素材。

## 4. 范围与非目标

### 4.1 本次范围

- 重做 `pages/home/index`
- 重做 `pages/discover/index`
- 重做 `pages/profile/index`
- 新增微信端自定义 `tabBar`
- 为 3 页补齐统一的滚动状态壳
- 为 3 页补齐静态 mock 数据
- 补充少量前台壳层组件

### 4.2 非目标

- 不接 `apps/api` 真实接口
- 不重构 `packages/*`
- 不改登录、报名、筛选、搜索、打卡、编辑主页等真实交互
- 不重做消息页、球队资产页的真实业务逻辑
- 不先上 `Skyline`
- 不做跨端视觉一致性工程

## 5. 方案选型结论

本次评估过 3 条路径：

1. `uni-app + WebView renderer + custom navigation + custom tabBar`
2. `uni-app + 页面级 Skyline`
3. 微信原生小程序重写这 3 页

最终选用第 1 条。

### 5.1 选用方案

第一阶段使用当前 `uni-app` 实现，微信端采用：

- `navigationStyle: custom`
- 自绘顶部导航壳
- `tabBar.custom: true`
- 自定义底部 tabBar
- 默认继续使用 `webview renderer`

### 5.2 不选 Skyline 的原因

`Skyline` 的主要价值在于：

- 更接近原生的滚动与渲染性能
- `Worklet` 动画
- 更复杂的页面转场和共享元素动画

但本次截图需求的核心是：

- 沉浸头部
- 滚动变色
- 吸顶分类
- 自定义 tabBar

这些能力在当前 `uni-app + 微信小程序 WebView renderer` 下即可完成，不构成必须切换 `Skyline` 的前提。

### 5.3 Skyline 升级条件

只有在后续真机验证出现以下问题时，才进入第二阶段技术升级：

- 长列表明显掉帧
- 头图压缩与吸顶联动不稳定
- 自定义 tabBar 与页面滚动出现明显层级异常
- 需要引入更强的高性能动画

在此之前不引入 `renderer: skyline`，避免第一阶段复杂度失控。

## 6. 页面与导航信息架构

为对齐截图，本次微信端主导航按以下视觉结构组织：

- `粗门`
- `打卡`
- 中央发布按钮
- `消息`
- `我的`

对应的页面路径在第一阶段映射为：

- `pages/home/index` -> `粗门`
- `pages/discover/index` -> `打卡`
- `pages/rumor-post/index` -> `消息`
- `pages/profile/index` -> `我的`

`pages/team/index` 保留页面文件与后续业务入口，但在第一阶段不继续占据底部主 tab 位。

这是一个刻意的信息架构调整，原因是截图的底部导航结构与当前项目 tab 结构不一致，而本次验收优先级是截图对齐。

## 7. 统一壳层设计

### 7.1 页面统一切到自定义导航栏

目标页统一使用 `navigationStyle: custom`。

原因：

- 系统导航栏无法实现截图中的沉浸式头部
- 系统导航栏无法实现滚动过程中的头部压缩与背景渐变
- 自定义导航栏可以复用现有胶囊位置测量能力

### 7.2 页面统一切到自定义 tabBar

目标页统一采用微信自定义 `tabBar`。

原因：

- 截图中的白底悬浮底栏与中央凸起绿色加号无法由原生 `tabBar` 实现
- 需要对不同 tab 页呈现统一的阴影、圆角、选中态图标与文字
- 需要保留中间按钮的独立点击区域与视觉突出

### 7.3 页面统一使用滚动状态机

3 个页面共享一套轻量滚动状态机：

- `top`
- `transition`
- `pinned`

同时共享一个核心插值变量：

- `headerProgress = clamp(scrollTop / threshold, 0, 1)`

所有顶部透明度、背景色、位移和缩放只依赖该值，不在各页面内写分散逻辑。

## 8. 滚动联动规则

### 8.1 首页与打卡页

顶部联动采用 3 段式：

- `0 ~ 40px`：轻微透明度变化
- `40 ~ 140px`：头部主要压缩区
- `140px+`：进入稳定 pinned 状态

表现规则：

- 背景从透明或浅绿雾感过渡到稳定浅绿或白底
- 搜索区逐步固定到安全区下方
- 分类 chips 吸顶
- 首屏头图或运营图逐步退出主视觉区

### 8.2 我的页

我的页采用“封面压缩”而不是简单吸顶。

表现规则：

- 大封面图在顶部完整展示
- 用户信息和编辑按钮浮在渐变遮罩之上
- 上滚后封面高度缩短
- 头像、昵称和统计信息向顶部稳定区收敛
- 二级 tab `我玩过的 / 票夹 / 影集` 吸顶

### 8.3 性能约束

第一阶段不引入复杂动画系统。

约束如下：

- 只使用简单插值和 class 切换
- 不做连续高频复杂计算
- 不依赖高成本阴影动画
- 不做共享元素或转场动画

## 9. 页面模块设计

### 9.1 `home`：粗门首页

首页以“运动社交入口”视觉为目标。

模块顺序：

1. 顶部沉浸区
2. 首屏双列推荐图卡
3. 一级横滑分类 chips
4. 二级分类流
5. 吉祥物提示条与筛选条
6. 活动卡片流

视觉重点：

- 顶部为浅绿雾感底，不是纯白栏
- 图卡体积大，圆角大，留白明显
- 卡片中的日期数字采用大号浅灰排版
- 卡片整体为白底高圆角，视觉偏内容社区

### 9.2 `discover`：打卡路线页

该页以“路线打卡流”视觉为目标。

模块顺序：

1. 顶部沉浸式头图海报
2. 路线卡片列表

每张卡片包含：

- 圆形路线 logo
- 标题
- 日期与地点
- 3 宫格图片
- Top1 / Top2 / Top3 头像
- 打卡人数文案
- 黑底绿色 `route 打卡` 按钮

视觉重点：

- 卡片比首页更低密度，更偏“展览卡”
- `route 打卡` 按钮是强品牌记忆点
- 上滚后头图完全退出，顶部进入稳定白栏

### 9.3 `profile`：我的主页

该页以“个人主页封面”视觉为目标。

模块顺序：

1. 全屏封面图
2. 左下头像、昵称、性别、关注粉丝、人格标签
3. 三组统计数字
4. 个性标签入口
5. 个性签名
6. 三宫格功能入口
7. 二级 tab
8. 空状态插画

视觉重点：

- 封面图必须主导首屏，不做普通 header
- 深色渐变遮罩必须足够重，保证白字可读性
- 页面下半部分为白色内容面板，与顶部封面产生清晰分层

### 10.3 组件职责

`MiniappPageShell`

- 负责安全区、页面背景、底部 tabBar 占位
- 不承载业务卡片逻辑

`FloatingCapsuleHeader`

- 负责顶部自绘导航

`HeroScrollScene`

- 不直接耦合具体页面内容字段

`useScrollScene`

- 负责滚动值和 `headerProgress`
- 输出统一阈值与滚动状态

## 11. Mock 数据策略

第一阶段全部采用静态 mock 数据。

要求如下：

- mock 数据单独放在 `src/mock/*`
- 字段结构尽量贴近未来真实页面结构
- 页面组件不直接内联大段静态数组

这样做的原因：

- 后续接接口时替换成本更低
- 页面模板可读性更高
- 不把第一阶段假数据写死成长期实现

## 12. 自定义 tabBar 规则

### 12.1 视觉要求

- 白底悬浮感
- 顶部微弱阴影
- 中间绿色凸起主按钮
- 左右常规 tab 图标与文字
- 选中态黑色图标与更深文字

### 12.2 行为要求

- 中间按钮独立于普通 tab 选中态
- 普通 tab 切页行为由自定义 tabBar 组件接管
- `消息` 页明确保持轻量占位，不纳入本次高保真重做

### 12.3 微信端约束

考虑到微信官方自定义 `tabBar` 的要求，第一阶段以微信小程序实现为准，不追求跨端完全复用。

## 13. 微信端技术结论

第一阶段技术结论固定为：

- 使用当前 `uni-app`
- 微信端启用 `custom navigation + custom tabBar`
- 默认保持 `webview renderer`
- 不先启用 `Skyline`
- 先完成截图级静态壳和滚动联动
- 真机评估后再决定是否进入 Skyline 第二阶段

## 14. 验收标准

第一阶段验收只看微信小程序端。

需要满足：

- 3 个页面首屏结构与截图高度接近
- 上滚后的导航栏变化方向与截图一致
- 底部 custom tabBar 与截图结构一致
- 页面不依赖真实接口即可稳定展示
- 页面之间切换不出现明显白屏或层级错乱

不要求：

- 像素级 100% 复制
- 真业务交互闭环
- 所有端统一表现

## 15. 风险与处理

### 15.1 tab 结构调整风险

为了对齐截图，本次主 tab 信息架构将与当前项目不同。

处理方式：

- 保留原有非目标页面文件
- 仅调整微信端主导航视觉入口
- 第一阶段只迁移 `home`、`discover`、`rumor-post`、`profile` 的底部主入口，不删除 `team` 页文件与已有路由

### 15.2 自定义壳层复杂度风险

顶部壳与 tabBar 一旦写散，后续维护成本会很高。

处理方式：

- 只抽最小公共壳
- 不抽业务卡片库
- 不引入超前设计系统

### 15.3 Skyline 决策摇摆风险

若第一阶段同时做截图复刻和 Skyline 适配，复杂度会明显上升。

处理方式：

- 先把视觉壳做完
- 再做真机验证
- 只有性能问题真实出现时才升级 renderer

## 16. 最终设计结论

本次截图对齐改造采用：

- 微信小程序端优先
- `uni-app` 继续承载实现
- 自定义导航栏
- 自定义 tabBar
- 统一滚动状态机
- 3 页静态高保真壳先落地

不采用：

- 第一阶段直接切 `Skyline`
- 微信原生重写
- 先接真实接口再调视觉

这个顺序最符合当前目标：先把产品界面和交互气质拉到截图水平，再决定后续真实业务接入和性能升级路线。
