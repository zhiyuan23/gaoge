# 高歌FC前台球队资产页面设计

日期：2026-05-22

## 目标

在 `apps/web` 的高歌 FC 球队页面中新增一个“球队资产”入口，并提供独立的前台资产明细页，面向普通访问者展示球队资产总览与收支记录。

本次目标是：

- 在现有 `teams/football` 页面中新增资产入口卡片
- 点击入口后进入独立的足球资产页面
- 资产页面展示资产总览：
  - 总收入
  - 总支出
  - 当前结余
- 资产页面展示收支明细列表
- 支持前台轻量筛选：
  - 全部
  - 收入
  - 支出
- 直接复用 `apps/api` 已有足球资产接口与共享类型

本次先完成设计，不在此文档中展开实现代码。

## 背景

当前仓库中，足球资产能力已经在后端和后台管理端落地：

- 后端资产接口位于 `apps/api/src/modules/football/asset-record/*`
- 管理端资产页面位于 `apps/admin/src/views/football/asset-record/*`
- 共享 contract 已存在于 `packages/shared/types/src/asset-record.ts`

当前 `apps/web` 中的球队页已经具备以下特征：

- 路由入口为 `/teams/:team?`
- 主要页面文件为 `apps/web/src/views/TeamsPage.vue`
- 足球球队页已经展示静态球队信息与赛季积分榜
- 前台请求层当前采用轻量 `utils` 封装，不存在复杂的模块化 API client

因此，这次不需要新增新的资产表或后端聚合模型，重点是把已有足球资产只读能力接入到前台球队页与独立资产页中。

## 范围

包含：

- 在 `apps/web` 中新增高歌 FC 球队资产入口卡片
- 新增独立的高歌 FC 资产页面
- 复用现有足球资产汇总接口
- 复用现有足球资产列表接口
- 支持前台 `全部 / 收入 / 支出` 三态筛选
- 约定前台加载态、空态、错误态与金额展示规则

不包含：

- 篮球资产页面同步实现
- 新增前台资产分页控件之外的高级搜索
- 新增关键字搜索、状态筛选、日期筛选
- 修改后台资产管理页
- 修改足球资产数据库结构
- 新增写接口、游客提交或前台编辑能力

## 方案对比

### 方案一：资产总览和明细直接堆在球队页

做法：

- 在 `TeamsPage.vue` 中直接新增资产总览区块和完整明细列表

优点：

- 路由改动最少
- 用户无需二次跳转

缺点：

- 当前球队页已经同时承载球队介绍与积分榜，再叠加资产列表会进一步拉长页面
- `TeamsPage.vue` 已经较重，继续塞入资产明细会提高维护成本
- 移动端阅读成本更高，信息层次会变差

### 方案二：球队页保留入口卡片，资产明细拆成独立页面

做法：

- 在高歌 FC 球队页中新增一个轻量资产入口卡片
- 点击后进入独立资产页
- 独立资产页承接总览、筛选和明细列表

优点：

- 信息架构清晰，球队介绍页与资产展示页职责分离
- 前台交互更接近“球队主页 -> 业务子页”的稳定结构
- 便于后续继续增加足球子页面

缺点：

- 需要新增路由和页面文件
- 用户查看资产需要一次跳转

### 方案三：只在球队页放入口，资产页一次性做成完整子模块框架

做法：

- 直接把 `teams` 域拆成更完整的子路由结构与更多复用组件

优点：

- 结构最完整

缺点：

- 对当前需求偏重
- 会把一次页面接入任务提前抽象成更大的前台架构调整

## 结论

采用方案二：球队页新增入口卡片，资产明细拆成独立页面。

具体原则：

- 保持 `TeamsPage.vue` 仍然以球队主页为主，不承载完整资产流水
- 只在高歌 FC 页面显示真实资产入口
- 独立资产页只做只读展示，不引入后台管理复杂交互
- 前台直接复用现有资产汇总和列表接口，不新增专门前台 API

## 信息架构

### 路由结构

保留现有：

- `/teams/football`
- `/teams/basketball`

新增足球资产子路径：

- `/teams/football/assets`

说明：

- 资产页属于高歌 FC 的子内容，因此路径继续挂在 `football` 语义下
- 本次不为篮球新增对等子路径，避免非目标范围扩散

### 页面职责

#### `TeamsPage.vue`

职责：

- 继续作为球队主页
- 在高歌 FC 视图中新增一个资产入口卡片
- 卡片只展示轻量总览信息和跳转动作

不负责：

- 渲染完整资产明细列表
- 承担复杂资产筛选逻辑

#### `TeamAssetPage.vue`

职责：

- 作为高歌 FC 独立资产页
- 展示资产总览区
- 展示筛选区
- 展示资产明细列表

不负责：

- 创建、编辑、删除资产记录
- 管理端级别的高级搜索和表格交互

## 数据基础复用

本次直接复用：

- `GET /football/asset-records/summary`
- `GET /football/asset-records`
- `@gaoge/shared-types` 中的：
  - `AssetRecord`
  - `AssetRecordListParams`
  - `AssetRecordListResponse`
  - `AssetRecordSummary`

这意味着：

- 前台不新增资产 contract
- 前台不复制一套本地资产字段定义
- 汇总口径完全以后端已确认逻辑为准

## API 设计

### 球队页入口卡片

页面进入高歌 FC 时，请求：

- `GET /football/asset-records/summary`

用途：

- 渲染入口卡片中的 `总收入 / 总支出 / 当前结余`

不请求列表接口。

原因：

- 球队主页只需要给出资产总览，不需要为入口预加载整份流水数据
- 减少主页请求体积和状态复杂度

### 独立资产页

进入资产页时并行请求：

- `GET /football/asset-records/summary`
- `GET /football/asset-records?page=1&pageSize=15`

当用户切换筛选时，请求：

- `GET /football/asset-records?page=1&pageSize=15&direction=income`
- `GET /football/asset-records?page=1&pageSize=15&direction=expense`

说明：

- 本次不新增额外后端参数
- 前台仅使用现有 `direction` 作为筛选入口
- 切换筛选时重置为第一页，避免不同筛选状态下分页错位

### 分页策略

虽然本次功能档位是“标准版”，重点在总览和筛选，但列表接口本身已经返回 `total` 并支持分页参数，因此本次保留轻量分页能力。

原则：

- 首屏默认 `page=1`
- 默认 `pageSize=15`
- 仅使用简单上一页 / 下一页或页码切换
- 不引入后台数据表格式的大型分页交互

原因：

- 资产记录会随着时间增长
- 若完全不分页，前台列表会持续膨胀
- 复用已有接口能力的成本很低

## 页面设计

### 球队页入口卡片

入口卡片位于高歌 FC 页面主体中，放在球队简介之后、积分榜之前。

展示内容：

- 标题：`球队资产`
- 副标题：说明这是球队公开资产总览
- 三个摘要值：
  - `总收入`
  - `总支出`
  - `当前结余`
- 一个 CTA 按钮：`查看明细`

视觉原则：

- 延续 `TeamsPage.vue` 现有深色背景和高对比卡片风格
- `结余` 为主视觉信息
- 收入与支出为辅助信息

### 独立资产页结构

页面从上到下分为：

1. 返回区
2. 页面标题区
3. 资产总览卡片区
4. 筛选区
5. 明细列表区
6. 空态或错误态区

### 返回区

保留明确返回入口：

- 返回高歌 FC 球队页

原因：

- 当前前台已有从子页返回首页的交互习惯
- 资产页需要和球队主页形成清晰往返关系

### 资产总览区

显示：

- 总收入
- 总支出
- 当前结余

本次不展示 `免收场次`，避免把后台汇总信息全部搬到前台，保持资产页总览足够聚焦。

### 筛选区

仅提供三个筛选项：

- 全部
- 收入
- 支出

交互规则：

- 默认选中 `全部`
- 切换筛选时重新请求列表
- 汇总区不随筛选切换而变化，始终展示全局汇总

原因：

- 用户对“球队总账”与“明细视图筛选”有不同心智
- 如果汇总值也被筛选状态影响，会造成口径理解混乱

### 明细列表区

每条记录固定展示：

- 标题
- 日期
- 金额
- 收支方向
- 记录类型
- 状态标签
- 描述
- 赛季标签
- 场次标签

展示规则：

- 按接口默认顺序展示，即时间倒序
- 前台不再自行排序
- 收入使用正向强调色
- 支出使用负向强调色
- `cancelled` 记录保留状态标记，但不参与前台额外计算

### 记录类型文案

前台统一映射为中文文案：

- `match_fee` -> `比赛收费`
- `extra_income` -> `额外收入`
- `equipment` -> `装备支出`
- `activity` -> `活动支出`
- `other_expense` -> `其他支出`

原因：

- 前台不应直接展示枚举值
- 中文文案更符合当前球队页的展示语境

## 状态设计

### Loading

需要分开处理：

- 球队页入口卡片 loading
- 资产页汇总 loading
- 资产页列表 loading

原因：

- 避免单个请求阻塞整页
- 页面可以更平滑地局部反馈状态

### Error

错误态规则：

- 汇总请求失败时，入口卡片或资产页汇总区显示轻量错误提示
- 列表请求失败时，列表区显示错误提示和重试按钮
- 不因为单一请求失败直接让整页白屏

### Empty

空态规则：

- 汇总接口返回零值时仍正常展示卡片
- 当列表为空时，显示：
  - `暂无资产记录`
  - `球队收支记录录入后会展示在这里`

## 格式化规则

### 金额

后端金额单位为分，前台统一转换为元显示。

统一格式：

- 汇总使用 `¥1,260.00` 这类稳定格式
- 列表项收入显示 `+¥20.00`
- 列表项支出显示 `-¥178.00`

### 日期

前台列表使用简洁日期格式：

- `2026-05-10`

若需要更完整时间，可在次级信息中展示，但本次不要求显示 `createdAt`。

## 实现边界

新增或调整的文件范围：

- `apps/web/src/router/index.js`
- `apps/web/src/views/TeamsPage.vue`
- `apps/web/src/views/TeamAssetPage.vue`
- `apps/web/src/utils/football.js`

不新增单独复用组件。

原因：

- 入口卡片与资产页总览虽然都展示汇总数据，但布局职责不同
- 当前 `apps/web` 结构较轻，本次直接在页面内实现更稳妥

## 验证方案

实现完成后至少验证以下内容：

### 静态校验

- `apps/web` 类型检查通过
- `apps/web` 构建通过

### 手动验证

- `/teams/football` 可看到资产入口卡片
- 入口卡片能正确显示汇总值或错误态
- 点击 `查看明细` 能进入 `/teams/football/assets`
- 资产页能显示汇总区与明细区
- `全部 / 收入 / 支出` 切换后列表会刷新
- 返回入口能正常回到球队页
- 接口失败时错误态不白屏
- 无数据时空态文案正常显示

## 非功能要求

- 保持当前 `apps/web` 的深色视觉语言，不单独引入后台风格
- 不为了这次需求引入新的状态管理库
- 不为了这次需求引入新的图表库或表格库
- 前台页面应优先保证移动端可读性

## 风险与约束

### `TeamsPage.vue` 已经较重

当前球队页已同时承载球队介绍与积分榜逻辑，因此入口卡片接入应尽量保持轻量。

应避免：

- 把完整资产列表逻辑直接继续塞进 `TeamsPage.vue`
- 在球队页中并行拉取不必要的资产明细数据

### 前台只读口径依赖后端现有逻辑

前台汇总和列表完全依赖当前足球资产模块既有返回结构。

这意味着：

- 前台不应自行重算汇总值
- 状态过滤、免收统计等业务规则以后端结果为准

### 篮球先不跟进

本次仅在高歌 FC 页面接入资产能力。

应避免：

- 为了“统一”而提前设计篮球占位 UI
- 在通用数据结构中加入当前无业务价值的篮球分支
