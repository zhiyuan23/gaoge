# Miniapp 球员列表调试页与请求层收敛设计

日期：2026-05-05

## 目标

在 `apps/miniapp` 中新增一个可手动访问的独立球员列表调试页，用于验证小程序端访问服务端接口的连通性。

同时，将 `apps/miniapp` 当前仍处于架构阶段的通用请求层，调整为以服务端真实响应结构为准进行解析，避免后续页面继续依赖过渡期的前端假设。

本次目标是得到一个最小但可复用的基础能力：

- 小程序能成功请求 `GET /football/players`
- 页面能明确展示加载成功、空数据、加载失败等状态
- 通用请求层能按服务端标准响应统一解包 `data`

## 背景

当前后端已经提供公开可读的球员列表接口：

- `GET /football/players`

接口挂载在 `apps/api/src/modules/football/player/player.controller.ts`，列表逻辑已由服务端完成：

- 默认分页参数
- 按 `playerNumber` 升序
- 返回 `{ list, total }`

当前小程序端现状：

- `apps/miniapp` 已有通用请求层 `src/api/request.ts`
- 该请求层当前写死了以 `code === 0` 作为成功判定
- `src/pages.json` 当前只注册了首页、登录页、我的页，没有球员调试页入口
- `src/api/football/players` 与 `src/pages/football/player` 目录已存在，但尚未形成一个可直接验证接口连通性的最小页面

这说明本次不需要从零创建一套业务域，只需要在现有目录中补齐最小闭环。

## 范围

包含：

- 新增一个独立可访问的球员列表调试页
- 为球员列表补齐小程序端 API 调用入口
- 调整 `src/api/request.ts` 的成功/失败解析逻辑
- 页面内明确展示加载中、失败、空列表、成功 4 类状态

不包含：

- 首页入口、tabBar 入口或菜单化导航
- 球员详情页
- 搜索、筛选、分页交互
- 编辑、新增、删除球员
- 小程序登录链路重构
- 通用 API SDK 抽象

## 设计原则

### 先打通链路，再扩展功能

本次页面的核心职责不是提供完整球员浏览体验，而是验证：

- 小程序环境变量是否正确
- 请求层是否能正确解析服务端响应
- 服务端球员接口是否可从小程序端直接读取

因此功能应收敛为只读列表页，不提前引入搜索、分页控件和复杂筛选。

### 请求层统一兼容服务端响应

既然 `apps/miniapp` 还处于架构阶段，就不应该继续把过渡期的响应假设写在业务页里。

本次采用统一解法：

- 请求层读取服务端标准包装
- 成功时返回 `data`
- 失败时优先使用服务端消息提示
- 页面层只消费业务数据，不再自行判断 `code`

这样后续 `teams`、`match-rounds` 等页面都可直接复用。

### 独立调试页不污染主导航结构

用户已明确要求页面为“独立页面手动访问”。

因此本次：

- 不把球员页加入首页跳转入口
- 不加入 tabBar
- 只在 `pages.json` 中注册路由，供开发期手动访问

这样既满足调试需求，也避免把临时验证入口混进正式信息架构。

## 页面与路由设计

### 页面路径

新增页面使用现有足球目录：

```text
apps/miniapp/src/pages/football/player/index.vue
```

在 `apps/miniapp/src/pages.json` 中注册页面：

- `pages/football/player/index`

标题建议使用：

- `球员列表`

该页面作为普通页面存在，不加入 tabBar。

### 访问方式

开发阶段通过手动跳转访问，例如：

- `uni.navigateTo({ url: '/pages/football/player/index' })`

如果后续需要临时调试按钮，可另行添加，但不属于本次设计范围。

## API 设计

### 小程序端 API 模块

在 `apps/miniapp/src/api/football/players` 下补齐一个最小读取方法，例如：

- `getPlayerList(params?)`

该方法只负责请求：

- `GET /football/players`

默认参数策略：

- `page = 1`
- `pageSize = 20`

本次页面不提供用户可编辑的分页交互，因此请求参数可以先在调用层固定。

### 返回结构

页面消费的数据结构以服务端实际返回为准：

```ts
{
  list: Player[]
  total: number
}
```

球员列表展示优先使用以下字段：

- `playerNumber`
- `nickname`
- `subTeam`
- `status`

如果部分字段为空，页面按占位文案展示，而不是报错。

## 请求层设计

### 当前问题

`apps/miniapp/src/api/request.ts` 当前把成功条件固定为：

- `code === 0`

但用户已明确要求“小程序以服务端返回结果为准进行修改”，因此这里不能继续保留前端写死判断。

### 目标行为

请求层需要兼容服务端标准响应包装，目标行为如下：

1. 成功响应：
   - 识别服务端成功 `code`
   - 返回 `data`

2. 业务失败响应：
   - 读取服务端错误消息字段
   - 默认 toast 展示该消息
   - 将错误对象继续 reject，便于页面感知失败态

3. 鉴权失败响应：
   - 保留现有清理本地登录态和跳登录页的能力
   - 但错误消息字段改为读取服务端真实字段

4. 非标准响应：
   - 如果返回的是字符串，先尝试 JSON 解析
   - 如果解析失败，按请求失败处理

### 服务端字段兼容策略

请求层优先兼容以下常见字段：

- `code`
- `data`
- `message`
- `errMsg`

消息读取优先级建议为：

- `message`
- `errMsg`
- 默认兜底文案

成功码判定以当前服务端标准为准，不再围绕旧小程序实现做历史兼容判断。

### 页面层约束

页面层不再关心：

- `code`
- `message`
- toast 时机

页面只需：

- 调用 API
- 处理返回的 `data`
- 在 Promise reject 时切换失败态并展示重试入口

## 页面状态设计

页面至少覆盖以下 4 类状态：

### 加载中

首次进入页面后立即拉取列表。

页面应展示明确的加载提示，而不是白屏。

### 加载失败

当接口请求失败或响应结构异常时，页面进入失败态。

失败态至少包含：

- 失败提示文案
- 重试按钮

这样可以快速区分“接口不通”和“页面无数据”。

### 空列表

当请求成功但 `list.length === 0` 时，展示空状态提示。

### 加载成功

成功态页面建议展示：

- 总数 `total`
- 列表项

每条列表项最少显示：

- 球员号码
- 昵称
- 所属分队
- 状态

布局保持简单，不引入复杂卡片交互。

## 页面结构建议

页面可以收敛为以下几部分：

1. 顶部状态区
   - 当前接口状态
   - 总数

2. 列表区
   - 成功时渲染球员列表

3. 异常区
   - 失败态或空态文案
   - 失败时提供重试按钮

如果项目内已有通用空态或状态组件，可复用；如果没有，就在页面内最小实现，不额外抽象。

## 数据流

页面数据流收敛如下：

1. 进入页面
2. 设置 `loading = true`
3. 调用 `getPlayerList({ page: 1, pageSize: 20 })`
4. 请求层统一按服务端响应解包
5. 页面拿到 `{ list, total }`
6. 根据结果切换为成功态或空态
7. 如果请求失败，切换为失败态

失败重试时重复以上流程。

## 错误处理

### 网络错误

请求层继续保留统一网络错误兜底提示，例如：

- `网络开小差了`

页面本身进入失败态，并允许再次请求。

### 业务错误

如果服务端返回非成功码：

- 请求层统一 toast 服务端消息
- 页面进入失败态

### 字段缺失

如果某个球员字段为空：

- 页面按 `-` 或等价占位文案展示
- 不因单个字段缺失导致页面整体失败

## 验证方案

本次至少验证以下内容：

1. 请求层能按服务端真实响应正确返回 `data`
2. 球员列表页能成功请求 `GET /football/players`
3. 成功时能看到 `total` 与列表项
4. 接口失败时页面能进入失败态
5. 空数据时页面能进入空态

代码层优先执行：

- `pnpm --filter @gaoge/app-miniapp typecheck`

如果仓库里存在与本次无关的既有 typecheck 问题，应在实现结果中明确指出，而不是混淆为本次改动导致。

## 实施边界

本次实现完成后，应得到以下结果：

- 小程序请求层不再写死旧成功判断
- 小程序存在一个可直接访问的球员列表调试页
- 页面能清晰反映接口联通状态

本次不继续推进：

- 球员筛选
- 下拉刷新和触底分页
- 球员详情
- 首页调试入口
- miniapp 全量 API 模块改造

这些内容都应留到后续独立需求中处理。
